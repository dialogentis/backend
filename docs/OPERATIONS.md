# Эксплуатация Dialogentis

Команды выполняются из каталога backend на Linux-хосте с Docker Compose, Bash, `sha256sum` и [age](https://github.com/FiloSottile/age). Примеры используют имя рабочего проекта `dialogentis`. Выберите это имя один раз, поскольку от него зависят имена томов.

В production API запускается двумя процессами. Параметр `API_WORKERS` в `.env.production` задаёт число процессов для выбранной конфигурации сервера.

## Независимый журнал

Укажите в `.env.production` имя внешнего Docker-тома `DELETION_JOURNAL_VOLUME`. Том должен переживать потерю хоста с базой и артефактами, обеспечивать запись UID 10001 и подтверждать `fsync` на независимом долговечном хранилище. Если хранилище предоставляет отдельную точку монтирования, зарегистрируйте её как внешний том.

```sh
docker volume create --driver local \
  --opt type=none --opt o=bind --opt device=/mnt/independent-storage/dialogentis-journal \
  dialogentis-privacy
```

Присвойте корню точки монтирования UID 10001 и права 0700. При переносе существующего стенда поставьте приложение на паузу, перенесите весь актуальный журнал с сохранением владельца и прав и проверьте его до смены тома. На время восстановления остановите исходную установку, чтобы она не обновляла журнал одновременно с новой. Обслуживайте один активный экземпляр на журнал.

## Ежедневная копия

Сгенерируйте ключ age на отдельной защищённой машине. Разместите на сервере только `backup.recipients`. Строку публичного ключа для файла даёт `age-keygen -y`. Храните приватный ключ age отдельно от снимков. Файл конфигурации приложения, включая `ENCRYPTION_KEY` и `ENCRYPTION_KEY_VERSION`, сохраняйте в хранилище секретов. При восстановлении нужны значения соответствующей копии и доступ к актуальному журналу.

```sh
age-keygen -o backup.identity
age-keygen -y backup.identity > backup.recipients
bash ops/snapshot.sh backup .env.production dialogentis \
  /srv/dialogentis-backups /etc/dialogentis/backup.recipients
```

Подготовьте отдельный каталог для снимков, доступный только оператору. Команда на время копирования останавливает кабинет, API и процессы, которые меняют данные, затем запускает остановленные сервисы. PostgreSQL остаётся запущенным. Команда сохраняет зашифрованные dump и архив файлов, записывает SHA-256 и публикует готовый каталог `snapshot-…Z`. Успешный запуск удаляет снимки из этого каталога старше семи суток.

Настройте ежедневный запуск в окно обслуживания. Например, при серверном времени UTC следующая запись в crontab запускает копирование в 02:30. Настройте получение ошибок cron и проверку возраста последней успешной копии. Каталог снимков размещайте на отдельном носителе или реплицируйте на отдельный хост с тем же сроком хранения.

```cron
30 2 * * * cd /srv/dialogentis/backend && /bin/bash ops/snapshot.sh backup .env.production dialogentis /srv/dialogentis-backups /etc/dialogentis/backup.recipients
```

## Восстановление на пустой стенд

Подготовьте исходные параметры приложения и совместимые образы. Подключите актуальный независимый журнал. Используйте новое имя Compose-проекта и пустые тома PostgreSQL, артефактов и RabbitMQ. Рабочий проект остановите, если он использует тот же журнал. Правила DNS и доступ к публичным портам переключайте только после проверки. Снимок содержит данные пользователей и должен происходить из доверенного хранилища.

```sh
bash ops/snapshot.sh restore .env.production dialogentis-recovery \
  /srv/dialogentis-backups/snapshot-20261121T000000Z /run/secrets/backup.identity
```

Команда проверяет суммы и расшифровку обеих частей перед загрузкой данных. Затем она восстанавливает БД и файлы, применяет миграции и актуальный журнал, очищает истёкшие данные и выгрузки и возвращает недоставленные задания в outbox. API и рабочие процессы остаются остановлены. При ошибке оставьте проект изолированным, сохраните журналы команды и повторите восстановление в новом пустом проекте после устранения причины.

```sh
docker compose --env-file .env.production -p dialogentis-recovery \
  -f compose.yaml -f compose.production.yaml up -d --no-build --wait
```

На изолированном адресе проверьте `/api/health/ready`, вход, видимость данных только для участников, отсутствие удалённой и просроченной истории, ответ опубликованного агента через внешний API и выполнение задания из очереди. Запишите время снимка и готовности. Цели выпуска составляют 24 часа для RPO и 4 часа для RTO.

## Обновление и возврат версии

Храните версионные теги или digest образов обоих приложений и соответствующие файлы Compose и Caddy. В `.env.production` задавайте `BACKEND_IMAGE` и `FRONTEND_IMAGE` для установки. Перед обновлением создайте снимок, запишите текущие теги и проверьте совместимость обратного запуска со схемой БД и форматом журнала. Соберите или загрузите новые образы под новыми тегами, замените значения переменных и запустите.

```sh
docker compose --env-file .env.production -p dialogentis \
  -f compose.yaml -f compose.production.yaml up -d --no-build --wait
```

После запуска проверьте readiness, ответ опубликованного агента и состояние очереди. При совместимой схеме и журнале верните предыдущие теги и повторите запуск с теми же томами. Если старый код не поддерживает текущую схему, восстановите предобновительный снимок в отдельный проект с актуальным журналом. Формат журнала также должен поддерживаться версией, которую запускаете. Выберите исправленный совместимый образ, если этот формат уже изменился. Между созданием снимка и неудавшимся обновлением могут быть новые записи. Перед переключением на старую копию зафиксируйте этот интервал.
