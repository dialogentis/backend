# Архитектурные решения

## D008 · 2026-11-03 · Транзакционный outbox и роль диспетчера

Job и outbox создаются в транзакции tenant и защищены RLS; составной FK не допускает ссылку события на Job другой организации. Job хранит UUID организации без внешнего ключа на неё, чтобы состояние удаления могло пережить удаление tenant. Создающий задание сервис обязан до вызова проверить существование организации и членство.

Диспетчер использует отдельную роль с доступом только к служебному outbox и правом изменять `published_at`; данные организаций и Job ей недоступны. Одноразовый Compose-сервис создаёт эту роль через bootstrap-подключение и сохраняет случайный пароль в отдельном volume. API не получает bootstrap-пароль и volume диспетчера. Отправка подтверждается брокером до фиксации `published_at`. При потере подтверждения сообщение может быть доставлено повторно; идемпотентный worker и восстановление ещё предстоит реализовать до включения пользовательских задач.

## D001 · 2026-10-30 · Основание и инструменты

Используются CPython 3.14.6 с GIL, uv 0.11.29, Ruff 0.17.3, ty 0.0.95, pytest 9.2.0. Python закреплён в `.python-version` и digest Linux-образа. Зависимости приложения и dev-группы зафиксированы единым `uv.lock`. Версии FastAPI 0.162.0, SQLAlchemy 2.1.6, Pydantic 2.14.2, Alembic 1.20.1 получены установкой; эта ветка SQLAlchemy сохраняет API 2.x.

Локальный GHCR отвечал TLS-таймаутами. Поэтому в Docker только сам uv устанавливается через `pip install uv==0.11.29`, затем все зависимости проекта — исключительно через `uv sync --locked`. Второго менеджера зависимостей проекта нет. Кэш uv доступен только в build layer, runtime работает без root.

## D002 · 2026-10-30 · NLP на Linux

scikit-learn 1.9.1, python-crfsuite 0.9.12, google-re2 1.1.20251105 установлены и проверены train/predict в Linux arm64 на Python 3.14.6. Это smoke совместимости, а не отчёт качества AC-05. У CRFsuite отсутствует корректная информация типов для Cython-экспортов Trainer/Tagger; два точечных ty-ignore документируют именно это ограничение. Остальные проверки типов включены.

## D003 · 2026-10-30 · Taskiq

Taskiq 0.13.0, taskiq-aio-pika 0.6.1, aio-pika 10.2.1. Durable exchange/queues, persistent messages (адаптер), publisher confirms (проверяется у write channel), ручной `ack_type=manual`. Проверка проходит через реальный отдельный worker-процесс. Повторы middleware не включены. Прикладной Job/outbox и фиксация статуса в БД до ack ещё не реализованы; их реализация и аварийные тесты — S06. См. исходники установленного адаптера и [контракт ручного ack Taskiq](https://taskiq-python.github.io/guide/cli.html).

## D004 · 2026-10-30 · Роли и RLS

Bootstrap роль создаёт БД/две ограниченные роли. Миграции владеют таблицами, приложение — нет; обе роли без superuser/BYPASSRLS. FORCE RLS включён на organizations, memberships, agents, agent_drafts. UUID контекста задаются через параметризованный `set_config(..., true)` внутри транзакции. Составной FK предотвращает ссылку draft на агента другого tenant. Отсутствующий контекст закрывает доступ к tenant-данным. Аутентификация и проверка membership должны предшествовать установке контекста в будущих API/worker-сервисах; RLS не заменяет эту проверку. Users — глобальная auth-таблица, она не доступна через endpoint общего CRUD.

## D005 · 2026-10-30 · Compose и сеть

PostgreSQL 18.4, RabbitMQ 4.2, Python, Node 24 LTS, Caddy и Mailpit закреплены digest. Node 24 принят для воспроизводимой сборки фронтенда. Внутренняя сеть БД/broker закрыта, сетевой выход есть только у HTTP/SMTP компонентов. API получает только runtime-переменные; bootstrap и migration credentials туда не передаются. Локальные порты 18000/18080/18025 выбраны из-за занятого другим приложением порта 8000. Параметр PUBLIC_BASE_URL согласован с 18080.

Init-hook PostgreSQL оформлен SQL с `\getenv`, а не исполняемым shell: bind-mount Docker Desktop в данном окружении запрещает exec. Чистый старт проверяется отдельным временным Compose-проектом. Никакие чужие контейнеры/volumes не изменялись.

## D006 · 2026-10-30 · Доставка auth-писем

Письма подтверждения, восстановления и приглашения сохраняются атомарно с токеном в зашифрованный PostgreSQL email outbox. Отдельный процесс читает его с SKIP LOCKED, отправляет через стандартный smtplib и удаляет payload после подтверждения SMTP; временные ошибки сохраняют ограниченный backoff. Это самостоятельный узкий механизм для auth-писем, не готовая реализация Job/outbox для обучения на S06. Доставка at-least-once, ссылки одноразовые. При смене ключа надо предварительно опустошить очередь; keyring ещё не реализован.

## D007 · 2026-10-30 · Контракты и сессии

Error envelope приведён к ТЗ: request_id находится внутри error; заголовок X-Request-ID остаётся. ETag использует `"rev-N"`. Открытые auth-операции проверяют Origin; операции с cookie также требуют CSRF HMAC, привязанный к session token. Сессии непрозрачные, хранятся хешированными, имеют idle/absolute expiry. Транзакционная dependency завершается до отправки ответа, чтобы ошибка commit не выдавала клиенту успешный результат. Auth rate limits сериализуются advisory lock в PostgreSQL, не зависят от числа API-процессов. Для dev origins явно перечислены локальные порты; в production исключений нет.

Контейнер API доступен только на loopback и доверяет Caddy forwarded headers для определения адреса клиента. Вынос API на публичный адрес потребует ограничения доверенных proxy. Тестовый контур выделен в `dialogentis-test` и не пишет аккаунты в development-БД. Индекс гарантирует максимум одного владельца; запрет удаления последнего владельца обеспечен сервисом. Перевод ownership выполняется в транзакции под блокировкой организации.
