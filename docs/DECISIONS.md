# Архитектурные решения

## D055 · Выгрузки истории

Экспорт использует Taskiq и существующее хранилище временных артефактов. Задание хранит формат, метаданные фильтров и редакцию настроек. Реплики расшифровываются при подготовке в рамках текущего срока хранения и по действующим правам инициатора. Сохранённая маска используется и в выгрузке. CSV защищает ячейки от интерпретации как формул, в том числе при скрытых пробельных символах и полноширинных знаках.

Готовый файл сохраняется с отдельным контекстом шифрования, привязанным к организации и заданию. Скачивание требует действующих прав на историю в той же организации. Изменение редакции настроек закрывает прежнюю ссылку. Ссылка действует до 15 минут и не переживает запись с ближайшим сроком удаления. Очистка временных артефактов отсоединяет ссылку перед удалением файла.

## D054 · Поиск по сохранённым сообщениям

Запрос поиска передаётся в JSON-теле. Текст запроса и открытый текст сообщений остаются в памяти приложения. Сервер расшифровывает только доступные ходы текущей организации в пределах срока хранения и ищет подстроку после нормализации Unicode и регистра. Маркер скрытого значения сам не считается совпадением.

Поиск использует те же фильтры, что список диалогов. За запрос проверяется до 200 ходов и до 8 МиБ зашифрованных данных. Курсор позволяет продолжить внутри длинного диалога и возвращать каждый диалог один раз. При отключённом сохранении текста сервер отклоняет запрос и кабинет скрывает форму поиска.

## D053 · История диалогов

История отделена от зашифрованного состояния активного диалога и от квитанций повтора. Запись хода, смена статуса и квитанция фиксируются одной транзакцией. История хранит канал, версию, публикацию, порядок ходов и безопасную трассировку. События содержат UUID версии исполняемого агента, в том числе при передаче и возврате.

Исполнитель отдельно возвращает текст для хранения и маскирует чувствительные значения из текущих и приостановленных сценариев. Ответы на запрос чувствительного параметра скрываются целиком. При ошибке исполнения исходная фраза в историю не попадает. Реплики шифруются с привязкой к организации, диалогу и ходу. Повтор использует замаскированную версию сохранённого ответа. При отключении хранения остаются статусы и безопасная трассировка.

Доступ проверяется по членству и RLS. Чтение сразу учитывает действующий срок и настройку текста. Очистка истории выполняется при изменении срока и периодической сверке. Текстовый поиск, выгрузки и массовое удаление остаются в S12. Старые квитанции сохраняют прежний срок жизни и не переносятся в историю.

## D052 · Встраиваемый чат и его сеанс

Скрипт вставки загружает iframe с публичным UUID виджета. Сервер выставляет CSP frame-ancestors по точному списку сайта. Стороны обработчика postMessage сверяют окно-источник и origin. Между окнами передаются только подтверждение готовности и положение/размер окна.

Iframe передаёт свой origin и проверенный адрес родительской страницы при старте сеанса. Зашифрованный токен ограничен каналом и диалогом, действует 30 минут и хранится в памяти iframe. Каждый новый ход проверяет активность канала и список сайтов. Повторы используют те же идентификаторы хода. Сервер применяет ограничение 20 запусков в минуту с burst 5 на канал и на IP внутри канала.

Виджет и внешний API используют одни версии публикаций, очередь ходов и квитанции. Публичное представление содержит текст и технический статус. Текст вставляется через DOM без интерпретации разметки, ссылки ограничены HTTP(S).

## D051 · Настройки виджетов и разрешённые сайты

У каждого виджета публичный UUID и собственные настройки агента. Владелец и администратор управляют названием, приветствием, цветом, положением кнопки и разрешёнными сайтами. Составная ссылка и RLS ограничивают доступ организацией и агентом. PATCH использует If-Match и записывает имена изменённых полей в аудит.

Разрешённые сайты хранятся в виде точных origins. Сервер нормализует регистр, международные домены и порты по умолчанию, допускает loopback в development и отклоняет пути, подстановки и данные авторизации. Тот же список будет использован для политики встраивания и выдачи сеанса виджета.

## D050 · Публичный runtime и привязка диалога

Внешний API использует общий интерпретатор, зашифрованное состояние, квитанции ходов, журнал HTTP-действий и восстановление после обрыва. При создании диалог сохраняет ключ и идентификатор неизменяемой публикации. Переходы между агентами проверяются по версиям и хешам этой публикации. Публичное представление содержит сообщения и технический статус; трассировка остаётся в кабинете.

Поиск по SHA-256 предъявленного Bearer ограничен одной строкой через транзакционную политику RLS. Принятие запроса повторно проверяет срок, область и отзыв под той же блокировкой организации, что публикация и отзыв. Для сообщений PostgreSQL применяет 5 запросов/с на ключ и 10/с на организацию с burst 20. Запуски используют отдельные счётчики. Повтор с тем же ключом идемпотентности возвращает квитанцию без расхода лимита нового хода.

Ответ на запуск возвращает отдельный токен диалога. Отправка сообщения, чтение квитанции и закрытие требуют этот токен и исходный ключ API. Повтор запуска после смены публикации восстанавливает прежний токен и публикацию.

## D049 · Выдача и отзыв ключей внешнего API

Ключ закреплён за агентом составным внешним ключом. Администратор или владелец получает случайный 256-битный секрет один раз при создании. В базе остаётся SHA-256 и 12-символьный префикс для идентификации. Срок по умолчанию 90 дней, верхняя граница 365 дней. Права первого выпуска — `conversation:create` и `message:send`.

Таблица изолирована политикой RLS по организации. Создание и первый отзыв записываются в аудит без секрета. Повторный отзыв возвращает 204 и сохраняет время исходного отзыва. Удаление организации удаляет ключи вместе с агентами. Подключение Bearer-аутентификации, отметки последнего использования и лимитов относится к публичному runtime в S11.

## D048 · Публикации и откат

Публикация сохраняет неизменяемый список версий с идентификаторами и хешами артефактов. Составные внешние ключи привязывают указатель агента и версии публикации к одной организации. Смена указателя, увеличение ревизии агента и аудит фиксируются в одной транзакции. Для публикации и отката владелец или администратор передаёт текущую ревизию в If-Match.

Перед публикацией сервер проверяет граф, данные, артефакты, интеграции и достаточность тестовых примеров по активным намерениям. Для основной версии требуется успешный запуск в тестовом чате. При низких метриках нужна явная отметка с причиной, которую сохраняет аудит. Откат переключает указатель на сохранённую публикацию и отклоняется, если её зависимости в архиве. Подключение закреплённого списка версий к внешним диалогам проверяется вместе с публичным каналом.

## D047 · Передача диалога между закреплёнными версиями

При подготовке версии сервер проверяет доступность целевых версий в организации, совместимость параметров, отсутствие циклов и глубину цепочки. Интерпретатор загружает модели по мере переходов. Зашифрованное состояние хранит путь активной версии и параметры приостановленных вызовов. Возврат применяет пересечение настроенного соответствия и параметров, явно отмеченных в блоке возврата. При передаче без возврата текущий агент покидает диалог. Флаг текущей фразы применяется только пока фраза ещё доступна. Передача предыдущих сообщений через историю остаётся частью работ по хранению и маскированию истории.

## D046 · Реальные HTTP-действия тестового диалога

Режим закреплён за диалогом. По умолчанию используются тестовые ответы. Администратор или владелец может явно включить реальные запросы, передав ключ запуска. Перед запросом сервер проверяет текущие права, настройки интеграции и действующую аренду хода. Журнал фиксируется отдельной транзакцией до отправки. Ключ идемпотентности передаётся для изменяющих запросов, когда поддержка указана в настройках интеграции. Интерпретатор получает только разрешённые поля ответа, сопоставленные с параметрами. Неопределённый исход изменяющего запроса сохраняется и обрабатывается соответствующей веткой.

## D045 · Повтор запуска тестового диалога

Кабинет передаёт ключ запуска и сохраняет его в памяти открытого чата до получения определённого результата. Ключ привязан к организации, пользователю и агенту, а запись первого хода привязана к версии. База хранит только хеш токена диалога. Сервер может снова вывести токен с помощью ключа шифрования и параметров запроса. Повтор во время обработки получает 409 с Retry-After. Успешный повтор до следующего хода возвращает тот же диалог. После отключения истории доступен токен и статус, а текст зависит от политики хранения. До истечения записи повтор закрытого или потерянного диалога не запускает сценарий заново.

## D044 · 2026-11-18 · Внутреннее резервирование первого хода

До исполнения может создаваться приватный диалог с зашифрованным начальным состоянием и отдельной записью хода. Внешнее действие привязывается к той же аренде и журналу, что и последующие сообщения. Успешное начало сохраняет turn=0 и revision=1; потерянное действие восстанавливается с неизвестным исходом. Эти операции пока не подключены к маршруту: прежде необходимо обеспечить идемпотентное повторное создание диалога и безопасное восстановление токена после потери ответа.

## D043 · 2026-11-18 · Обмен HTTP-действиями с изолированным runtime

Дочерний процесс запрашивает действие по идентификатору блока и передаёт только входные slots, а сервер проверяет идентификатор по закреплённому снимку, типы значений и разрешённые выходные slots. Ответ и число действий ограничены; таймаут или отмена завершают дочерний процесс. Тестовый HTTP-режим использует тот же канал, но секреты и адреса интеграций в дочерний процесс не передаются. Канал сам по себе не авторизует сетевой запрос и не заменяет запись ledger до отправки. Начало диалога пока не резервирует receipt, поэтому live-режим не подключён.

## D042 · 2026-11-18 · Журнал внешних действий тестового хода

Для каждого внешнего действия подготовлен отдельный metadata-only ledger с UUID исполнения, организацией, интеграцией, блоком, номером действия и fencing token хода. Составные внешние ключи не допускают ссылок на чужой receipt или интеграцию. Перед отправкой вызывающий код должен зафиксировать запись `started`; один ход допускает до трёх последовательных действий. Завершение требует действующего токена и не принимает повторную фиксацию. Пока действие выполняется, завершение хода запрещено. Просроченный ход помечает незавершённые действия как `unknown_result`, не выполняя их повторно. Удаление receipt каскадно удаляет журнал; пока запись журнала существует, интеграцию можно отключить, но нельзя удалить, в том числе после завершения диалога.

Операции журнала пока внутренние и не отправляют запросы сами: проверка принадлежности блока неизменяемому сценарию, обязательная транзакционная фиксация перед вызовом HTTPS-клиента и логика ветвления должны быть обеспечены связывающим сервисом до включения внешних действий. Ledger сейчас связан с receipt тестового чата; публичные каналы требуют соответствующего расширения. Локальный журнал не гарантирует exactly-once на стороннем сервисе.

## D041 · 2026-11-18 · Внутренний HTTPS-клиент интеграций

Подготовлен отдельный клиент на публичном network-backend API httpcore: перед соединением он проверяет все DNS-ответы и подключается к проверенному IP, сохраняя исходный hostname для SNI и проверки сертификата. Не используются proxy, redirect и повторная отправка запроса; приватные, служебные, multicast и переходные IPv6-адреса отклоняются. Методы и пути сверяются с конфигурацией: путь, заканчивающийся на `/`, разрешает вложенные пути, остальные совпадают точно. Время ограничено восемью секундами и оставшимся бюджетом, размер JSON-ответа — 256 КиБ. Изменяющий запрос при потере результата получает `unknown_result`. Отладочная трассировка httpcore для этих вызовов не пишет заголовки и содержимое.

Клиент ещё не подключён к runtime: вызывающий код обязан сперва записывать execution ledger и не повторять неопределённые изменения; также нужны лимит трёх вызовов на ход, настройка поддержки Idempotency-Key, безопасное сопоставление разрешённых полей ответа и проверка прав live-режима. Передаваемый секрет используется как Bearer-токен; выбор других схем авторизации пока не реализован. Документация используемой библиотеки: [network backends httpcore](https://www.encode.io/httpcore/network-backends/).

## D040 · 2026-11-18 · Управление интеграциями

Владелец и администратор могут создать, изменить, отключить и удалить интеграцию, а также заменить её секрет. Метаданные и шифротекст изолированы RLS по организации; секрет зашифрован AES-GCM с привязкой к организации и интеграции и никогда не возвращается в API. Изменения используют ревизию и записываются в аудит. Удаление блокируется при ссылке из черновика или снимка версии; удаление организации очищает и интеграции. Участники могут просматривать метаданные и признак наличия секрета.

При сохранении проверяются HTTPS-адрес, структура пути, методы и очевидно непубличные IP-адреса. Это только проверка конфигурации; подготовленный позже сетевой клиент описан в D041. Никакие внешние HTTP-вызовы управлением интеграциями не выполняются. Нет keyring для чтения старых секретов после смены ключа, поэтому ротация ключа установки без переходного механизма недопустима. Выбор интеграции в блоке сценария и полноценный runtime остаются на S09.

## D039 · 2026-11-17 · Настройки хранения текста

Владелец и администратор изменяют название, срок хранения и сохранение текста с `If-Match` по отдельной ревизии настроек. Операция блокирует организацию и фиксирует изменение и событие аудита атомарно. Отключение немедленно запрещает запись и повторное чтение текста ответов; по явному выбору ранее сохранённые шифротексты receipt удаляются в той же транзакции, а идентификаторы остаются для защиты от повторного выполнения. В кабинете при отключении удаление отмечено по умолчанию, но не включается повторно при последующем редактировании уже отключённой настройки.

Сокращение срока немедленно удаляет старые шифротексты receipt, периодическая очистка применяет срок к оставшимся записям по времени БД. Сейчас это относится только к ответам тестового чата; полноценная история, её экспорт и удаление, а также применение политики к резервным копиям ещё не реализованы. Физическое удаление из WAL и существующих резервных копий этим обновлением не подтверждается.

## D038 · 2026-11-17 · Ошибки сценария тестируемой версии

Перед загрузкой модели тестовый чат проверяет структуру сценария именно неизменяемой выбранной версии. При ошибках API возвращает 409 `invalid_version_flow` и до 100 безопасных сообщений проверки; кабинет показывает причину и советует исправить черновик и обучить новую версию. Проверка выполняется после авторизации и проверки принадлежности версии, поэтому чужой пользователь не получает её диагностику.

Это та же частичная структурная проверка, которую использует внутреннее ядро; она не подтверждает полную готовность к публикации. Если после обучения изменён черновик, результаты проверки текущего черновика могут отличаться от ошибок старой версии.

## D037 · 2026-11-17 · Остановка API с активными тестовыми ходами

При штатном завершении API сервис перестаёт принимать новые тестовые ходы, ожидает удерживаемые фоновые задачи до 30 секунд и отменяет оставшиеся до закрытия пула БД. В Compose API получает 65 секунд на остановку, чтобы оставить время действующим HTTP-запросам и завершающимся задачам. При принудительном завершении, падении процесса или прерывании ожидания незавершённый ход остаётся на восстановление watchdog как неизвестный результат.

Тайм-аут ожидания не является жёсткой границей остановки: очистка дочернего процесса или защищённая файловая операция могут задержать завершение отменённой задачи. Остановка реального контейнера во время выполняющегося хода пока отдельно не проверена.

## D036 · 2026-11-17 · Management API тестового чата

Участник пространства может создать тестовый диалог для готовой версии и отправить сообщение через management API. Используются существующие cookie, проверка Origin и CSRF, а также отдельный токен диалога и ключ идемпотентности. Ответ содержит сообщения и безопасную трассировку; внутреннее состояние и значения параметров не возвращаются. В первой реализации разрешён только режим mock, реальные HTTP-действия ещё не подключены. Сервис и исполнитель переиспользуются в процессе API.

Кабинет открывает тест выбранной готовой версии на экране обучения и удерживает токен, сообщения и ключ незавершённого запроса в памяти компонента. Повтор использует прежние идентификаторы; при отключённом хранении текста недоступный ответ не подставляется как сообщение агента. При смене версии или организации локальное состояние уничтожается. Идемпотентное создание диалога, реальное HTTP-отключение, graceful shutdown, полная проверка графа и поддержка остальных блоков остаются незавершёнными. Версия может иметь статус готовой модели при непроверенном сценарии; некорректный граф не исполняется.

## D035 · 2026-11-17 · Общий предел исполнения runtime

Внутренний тестовый чат использует четыре общеплатформенных слота PostgreSQL перед загрузкой модели и запуском дочернего исполнителя. Ожидание слота входит в 20-секундный бюджет исполнения. Пока слот занят, отдельная проверка следит за соединением; при его потере работа отменяется. При завершении, исключении или отмене соединение закрывается, чтобы не вернуть удерживаемую блокировку в пул. Дополнительный локальный семафор исполнителя остаётся в силе.

При сетевом разделении старый и новый процессы могут кратко пересечься до обнаружения потери соединения; fencing состояния не позволяет устаревшему ходу записать результат. Лимит не является замером производительности и не покрывает будущие пути runtime, пока они явно не подключены к этому механизму. Требуется нагрузочная проверка, в том числе потребления памяти, стоимости отдельных соединений и ожидания слота.

## D034 · 2026-11-17 · Отключение клиента во время тестового хода

Внутренний сервис исполняет сообщение в отдельной удерживаемой задаче и защищает её от отмены вызывающего запроса. Отмена ожидания не отменяет вычисление и фиксацию результата; повтор с теми же идентификаторами получает сохранённый ответ или состояние обработки. Исключения отсоединённых задач считываются без записи текста в журнал. Внутренний лимит времени и проверка прав перед сохранением сохраняются.

Это проверено на отмене вызывающей корутины, а не на разрыве реального HTTP-соединения: маршрут ещё не подключён. При остановке процесса незавершённый ход по-прежнему восстанавливается как неизвестный через watchdog; гарантии завершения внешних действий после падения процесса нет. Нужны HTTP-проверка, управление завершением приложения и общеплатформенный лимит параллелизма.

## D033 · 2026-11-17 · Наблюдение за зависшими ходами

Отдельный Compose-процесс проверяет истёкшие резервирования с паузой пять секунд между проходами. Для обнаружения организаций используется ограниченная роль диспетчера; содержимое диалогов этой роли недоступно. Обработка каждой организации выполняется в её контексте, ограничена по времени и размеру пакета; сбой одной организации не прерывает проверку остальных. Существующая минутная сверка остаётся дополнительным механизмом восстановления. Оба процесса используют блокировки строк и не выполняют ход повторно.

Фактическое время восстановления зависит от доступности БД, блокировок и нагрузки. Интервал проверки сам по себе не доказывает гарантию 60 секунд; её нужно подтвердить на целевой нагрузке и при отказах. Подключение watchdog не устраняет остальные ограничения D032.

## D032 · 2026-11-17 · Идемпотентные ходы внутреннего тестового чата

При резервировании хода в той же транзакции создаётся receipt с идентификатором сообщения, хешем ключа идемпотентности и HMAC запроса. Повтор с теми же идентификаторами и текстом возвращает сохранённый результат без выполнения модели; переиспользование идентификатора с другим запросом отклоняется. Состояние и результат фиксируются атомарно. При отключённом хранении текста ответ не записывается и повтор сообщает, что восстановить его нельзя. Доступ к повтору ограничен автором, членством в организации и токеном диалога.

Неизвестный результат после истечения резервирования помечается отдельно и не выполняется повторно. Метаданные сохраняются до 24 часов после окончания диалога, но после удаления или истечения самого диалога повторный ответ недоступен. Текст ответа шифруется при включённом хранении; изменение настройки на отключённую скрывает ранее сохранённый ответ, однако удаление ранее сохранённого текста ещё не реализовано. Ротация ключей, история и маскирование чувствительных данных, публичный маршрут и гарантии завершения при отключении клиента остаются в работе. Планировщик пока не обеспечивает восстановление за 60 секунд.

## D031 · 2026-11-17 · Хранилище receipt

Для будущих receipt создана таблица с принудительной RLS, отдельной уникальностью ключа и идентификатора сообщения в диалоге и ограничением формата зашифрованного ответа. Запись может пережить удаление истёкшего диалога; удаление организации удаляет её каскадно. Планировщик находит организации с receipt через ограниченную служебную роль и очищает записи по указанному сроку. Проверены уникальность, изоляция, шифротекст, ограниченные права и очистка.

Схема сама не обеспечивает идемпотентность; последующее подключение сервиса и оставшиеся ограничения описаны в D032.

## D030 · 2026-11-17 · Защита данных для идемпотентности

Подготовлены криптографические операции для будущих receipt: ключ идемпотентности хешируется, а отпечаток сообщения вычисляется HMAC с привязкой к организации, диалогу и идентификатору сообщения. Ответ и безопасная трасса могут быть зашифрованы AES-256-GCM с привязкой к организации, диалогу и ходу; используются отдельные ключи назначения. Проверены подмена, перенос и изменение запроса; исходный текст не входит в отпечаток в открытом виде.

Подключение к сервису описано в D032. Смена ключа без поддержки старых версий делает старые отпечатки и ответы недоступными; ротацию нужно реализовать до использования этого механизма в API.

## D029 · 2026-11-17 · Токен тестового диалога

При создании внутренний сервис выдаёт случайный токен диалога; в БД хранится только SHA-256 хеш. Для чтения, резервирования и сохранения хода проверяются токен, пользователь и членство в организации. Неправильный токен возвращает тот же 404, что отсутствующий диалог; токен исключён из представления объектов и возвращается только при создании. Существующие внутренние записи без хеша после миграции недоступны и удаляются при истечении срока.

HTTP-маршрут и передача токена в заголовке ещё не реализованы. Идемпотентное восстановление утерянного ответа о создании и политика отзыва токенов остаются будущей работой; токен нельзя помещать в URL или журналы.

## D028 · 2026-11-17 · Внутренний путь тестового диалога

Внутренний сервис получает готовую версию и модель из tenant-хранилища, запускает D026 вне транзакции и сохраняет состояние через D025/D027. Для продолжения он сначала проверяет автора, ревизию и срок, затем резервирует ход; после вычисления заново проверяет членство и токен. Результат возвращается только после commit. Проверены настоящая обученная подписанная модель, защита от чужого пользователя, устаревшей ревизии и отзыв доступа во время вычисления.

Это ещё не публичный интерфейс: отсутствуют receipt и идемпотентность, гарантия завершения при разрыве клиента, 60-секундное восстановление и платформенный лимит нескольких процессов. Токен внутреннего диалога описан в D029. Тайм-аут сервиса 25 секунд включает этапы запроса, но защищённое чтение файла завершает операцию до обработки отмены, поэтому жёсткая граница всего запроса не подтверждена. Текст и результаты находятся в памяти и каналах, checkpoint — зашифрован; история сообщений и трассы пока не сохраняется.

## D027 · 2026-11-17 · Резервирование хода тестового диалога

Перед вычислением внутренний сервис резервирует ход на 30 секунд случайным токеном. Второй запрос получает 409 с Retry-After, а запись результата разрешена только с действительным токеном и ожидаемой ревизией. При истечении резервирования обслуживание помечает диалог завершённым и удаляет состояние, не повторяя потенциально выполненный ход. Проверены конкуренция, чужой и истёкший токены и восстановление записи.

Планировщик запускается раз в минуту, поэтому восстановление может занять до 90 секунд с начала хода при нормальной работе; требование восстановления за 60 секунд ещё не подтверждено. Идемпотентные receipt, защита внешних действий и публичный маршрут ещё не реализованы. Дочернее исполнение пока не подключено к резервированию.

## D026 · 2026-11-16 · Ограниченное исполнение хода

Внутренний исполнитель передаёт снимок, сообщение, состояние и подписанную модель дочернему процессу через ограниченные каналы; вывод ошибок дочернего процесса подавляется. В дочернем процессе проверяются хеш снимка, подпись и принадлежность модели, после чего используется общее ядро runtime. При тайм-ауте или отмене процесс завершается и ожидается его выход. На одном экземпляре исполнителя одновременно допускается до четырёх процессов; ожидание очереди и работа ребёнка входят в тайм-аут до 20 секунд. Проверены реальная обученная модель, неверные снимок и организация, отмена, тайм-аут и ограничение конкуренции.

Это пока внутренний компонент без API: сериализация запроса и чтение артефакта до запуска не входят в его тайм-аут. Для общего бюджета хода, ограничений памяти и платформенной конкуренции нескольких процессов API требуется дополнительное управление. Вызывающий код должен переиспользовать экземпляр исполнителя, получать модель через проверенное хранилище и не записывать передаваемый текст, результат или открытый чекпоинт в логи. Производительность под целевой нагрузкой ещё не измерялась.

## D025 · 2026-11-16 · Внутренние операции состояния тестового диалога

Внутренний сервис проверяет подтверждение почты и членство, разрешает наблюдателю создать собственный диалог и скрывает диалоги других авторов. Создание допускается только для готовой версии указанного агента. Чтение и запись проверяют 30-минутный idle и 24-часовой абсолютный срок по времени БД после получения блокировки. При записи проверяется ожидаемая ревизия, версия и следующий номер хода; при завершении или ошибке шифротекст удаляется сразу. Состояние всегда шифруется кодеком D022; передача ему завершённого состояния с параметрами запрещена.

Транзакция блокирует организацию и строку диалога, поэтому изменение прав и конкурентная запись не проходят незамеченными; проверен конфликт одновременных ходов. Сервис принимает состояние только от доверенного вызывающего кода: он сам не проверяет его соответствие снимку графа и не исполняет модель. До HTTP-маршрута нужны создание состояния из выбранной версии, проверка model-артефакта, жёсткий тайм-аут и лимит параллелизма, токен диалога и безопасная диагностика. Проверка ревизии после вычисления не предотвращает повтор внешнего действия; для HTTP потребуется отдельный execution ledger.

## D024 · 2026-11-16 · Очистка истёкших тестовых диалогов

Минутное обслуживание получает от ограниченной служебной роли только UUID организаций с тестовыми диалогами. Затем в контексте каждой организации оно удаляет истёкшие записи пакетами по 100, не ожидая занятых строк; активные и заблокированные строки не удаляются. Проверены обнаружение организации без outbox, отсутствие у служебной роли доступа к состоянию, повторный запуск и пропуск заблокированной записи.

За один проход обрабатывается не более 1000 записей организации; остаток и пропущенные блокировки повторяются на следующем проходе. При остановленном планировщике или крупном накопившемся хвосте очистка может задержаться; гарантия очистки в течение часа ещё требует эксплуатационной и нагрузочной проверки. Доступ к диалогам по сроку и мгновенное удаление состояния завершённого диалога должен обеспечивать будущий сервис.

## D023 · 2026-11-16 · Основа хранения тестовых диалогов

Миграция создаёт таблицу внутренних тестовых диалогов с принудительной RLS организации, составной ссылкой на конкретную версию агента, ревизией и сроками жизни. Поле состояния ограничено размером и форматом шифротекста DGC1; при удалении версии или организации запись удаляется каскадно. Проверены шифрование и восстановление, запрет чтения из другой организации и без контекста, неверная ссылка, ограничения формата и срока, удаление вместе с организацией.

Это только основа хранения: заголовок в БД не подтверждает подлинность шифротекста без кодека, доступ по участнику/роли, атомарное обновление и проверка сроков при обращении ещё не реализованы. Периодическая очистка описана в D024. До внедрения сервиса и проверки готовности версии таблица не используется для пользовательских диалогов.

## D022 · 2026-11-16 · Шифрование состояния диалога

Внутренний кодек шифрует весь сериализованный чекпоинт AES-256-GCM со случайным nonce. Ключ выводится из `ENCRYPTION_KEY` с отдельной меткой назначения; версия ключа записана в заголовке. Аутентифицированный контекст связывает данные с организацией, агентом, версией и диалогом, поэтому изменение или перенос шифротекста отклоняется. Ошибки не содержат значений. Проверены восстановление действующего состояния, сокрытие чувствительных значений и отклонение подмены.

Кодек сам по себе не хранит данные и не проверяет права, срок жизни или повторное использование старого состояния; эти проверки и атомарная запись необходимы в сервисе диалогов. Ротация нескольких версий ключей пока не реализована: смена ключа делает старые чекпоинты недоступными. Внутренний `RuntimeState.model_dump_json()` по-прежнему содержит открытые значения и не должен напрямую записываться в БД, логи или API.

## D021 · 2026-11-16 · Внутреннее исполнение условий

Условие содержит упорядоченные UUID ветвей и обязательный выход `else`. Поддерживаются `eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `in`, `exists` и композиции `all`/`any` глубиной до трёх. Параметры и константы проверяются по типу, числа сравниваются без потери десятичной точности; отсутствующее или пустое значение не удовлетворяет сравнению, а `0` и `false` считаются существующими. Интерпретатор выбирает первую подходящую ветвь без выполнения пользовательского кода. Ссылки проверяются при сохранении и импорте; при копировании UUID ветвей и вложенных параметров переназначаются. Незавершённые условия разрешены в черновиках и переносе, но не проходят проверку сценария. Редактор позволяет настроить вложенные условия, порядок ветвей и связи; удаление ветви удаляет её связь.

## D020 · 2026-11-10 · Присваивание параметров

Блок `set_slot` присваивает типизированную константу или значение другого параметра того же типа, либо очищает параметр. Выход `next` используется после успешного действия, `error` — если исходный параметр не заполнен. Значение `0` или `false` считается заполненным; десятичные числа сохраняются строкой. Ссылки проверяются при сохранении, импорте и копировании, при копировании идентификаторы заменяются. Пользовательские выражения не исполняются. Источник из ответа HTTP пока недоступен: он относится к ещё не реализованным HTTP-действиям.

## D019 · 2026-11-10 · Сбор параметров в сценарии

Блок `ask_slot` ссылается на UUID параметра и необязательной сущности, содержит вопрос, от одной до пяти попыток и декларативные проверки длины, границ числа или шаблона RE2. Выходы `success`, `invalid` и `exhausted` настраиваются на схеме и в форме. Параметр может быть получен из сущности текущей фразы либо из ответа на вопрос; одно сообщение нельзя повторно использовать для нескольких блоков. Словарная сущность передаёт каноническое строковое значение, поэтому десятичная точность не теряется. Проверка графа, импорт и копирование учитывают ссылки и типы; при копировании UUID переназначаются.

Внутренний чекпоинт содержит значения и счётчики попыток; при завершении или ошибке они очищаются. Значения исключены из трассировки и представления объектов, но сериализация чекпоинта содержит их открытым текстом. До сохранения состояния или подключения любого API необходимо зашифровать чувствительные значения и обеспечить изоляцию организации. Семантический хеш теперь включает определения сущностей; старые временные чекпоинты несовместимы. Внешний жёсткий timeout модели по-прежнему необходим.

## D018 · 2026-11-10 · Первое ядро диалога

Внутренний синхронный интерпретатор выполняет start, say, switch_intent, fallback и end; другие блоки возвращают `unsupported_in_stage`. Чекпоинт содержит UUID версии и хеш семантики графа, параметров и намерений; положение блоков и layout на хеш не влияют. Одно сообщение распознаётся не более одного раза за ход. Трасса содержит идентификаторы, переходы и безопасные коды без исходного текста или значений параметров. После трёх неудач агент показывает явно заданный владельцем пример, если он есть, и завершает диалог; пример не извлекается автоматически из обучающих данных. Отсутствие примера показывается предупреждением в проверке графа.

Ядро проверяет не более 50 переходов и прошедшие 20 секунд между операциями. Синхронный вызов модели нельзя прервать изнутри этого ядра: до подключения к API требуется внешний жёсткий timeout и ограничение параллелизма. Сохранение состояния, идемпотентность, обработка остальных блоков, изоляция и защита значений параметров пока не реализованы; ядро не открыто как публичный или тестовый чат.

## D017 · 2026-11-10 · Текстовые шаблоны ответов

Ответы используют только подстановки `{{slot_code}}` с необязательными пробелами внутри скобок. Шаблон проверяется на известные параметры, допустимый синтаксис, отсутствие HTML и ограничение 4000 символов. Рендерер возвращает обычный текст, проверяет типы значений, подставляет значение по умолчанию или пустую строку для отсутствующего необязательного параметра и сообщает об отсутствии обязательного; длина результата также ограничена 4000 символами. Значения не интерпретируются как шаблоны или HTML, а ошибки не содержат исходный текст и значения. Рендерер подключён к внутреннему ядру; тестовый и публичный чаты ещё не реализованы.

## D016 · 2026-11-10 · Определения параметров диалога

Параметр хранит UUID, код, название, тип, признаки обязательности и чувствительности и необязательное значение по умолчанию. Целые значения ограничены точным диапазоном JSON/JavaScript, десятичные передаются строкой без экспоненты, даты — ISO, логические значения — без приведения типов. При копировании UUID параметров заменяются, а коды и значения остаются прежними. Удаление и переименование параметра, на который ещё ссылается сценарий, блокируется; JSON-импорт и экспорт сохраняют параметры. Существующие черновики с неполными параметрами читаются как раньше и проверяются при сохранении. Флаг чувствительности пока только хранится: шифрование и маскирование значений относятся к runtime и ещё не реализованы.

## D015 · 2026-11-10 · Выходы по намерениям

Выход `switch_intent` хранится в `source_handle` как канонический UUID намерения; отдельный выход `fallback` остаётся строкой `fallback`. Это позволяет переименовывать намерение без изменения связи. Ссылки проверяются при сохранении, импорте и копировании: отсутствующее намерение запрещено, отключённое сопровождается предупреждением. При копировании UUID выхода переназначается на идентификатор скопированного намерения. Редактор предлагает соединение на схеме и выбор целевого блока с клавиатуры.

## D014 · 2026-11-10 · Выполнение обучения и отчёт

Training worker получает глобальную advisory-блокировку PostgreSQL до захвата Job и выполняет CPU-часть в дочернем процессе. Дочернему процессу передаётся только снимок и необходимые параметры подписи; данные БД и брокера в его окружение не передаются. Промежуточные модель и отчёт записываются в анонимные временные файлы. При отмене или timeout процесс завершается, а при гибели родителя завершает работу после закрытия канала. Этапы отражают реально начатые операции; процент не выдумывается. Heartbeat работает в родителе независимо от вычислений.

До фиксации проверяются подпись, принадлежность модели и хеши обучения. Под актуальным fencing token в одной транзакции резервируется квота, публикуется артефакт, записывается отчёт и завершается Job. Повторная доставка терминального задания ничего не создаёт. При потере worker обучение автоматически не повторяется. Соединение, удерживающее глобальный слот, проверяется каждую секунду с тайм-аутом 2 секунды; при сетевом разделении короткое перекрытие вычислений до обнаружения отказа не исключено, но fencing не позволяет устаревшей попытке записать результат.

API и кабинет показывают реальные метрики и постраничные ошибки из неизменяемого test-снимка. Для непроверенного графа отчёт возвращает `not_checked`, а интерфейс предупреждает, что перед публикацией нужна проверка. Пустые выборки не подменяются нулями. Отдельно сообщается о недостаточном числе тестов. Доступ к версиям и отчётам имеют участники пространства; запуск доступен редактору и выше, отмена — автору либо администратору.

## D013 · 2026-11-10 · Снимок версии и задание обучения

Внутренний сервис подготовки под блокировкой организации проверяет роль, сохранённую ревизию и набор данных, затем в одной транзакции создаёт снимок AgentVersion, Job и outbox. Повторный ключ идемпотентности ограничен организацией, агентом и автором; тот же ключ с другой ревизией отклоняется. Блокировка и проверка активного Job не допускают двух незавершённых обучений одного агента. На уровне БД снимок, идентификаторы и хеши защищены от изменения; результат разрешено записать только один раз со ссылкой на готовый model-артефакт той же организации. Удаление организации удаляет версии до артефактов и заданий.

Статус версии вычисляется из связанного Job: queued/running — building, cancelled — cancelled, succeeded с артефактом и отчётом — ready, остальные случаи — failed. Это исключает отдельный рассинхронизированный статус. `config_hash` учитывает весь снимок, `nlu_hash` — упорядоченные определения и train-примеры с настройками без графа и test-примеров; изменение названий или настроек консервативно меняет nlu_hash. Пока настройки в снимке фиксируются начальными порогами, редактирование порогов в черновике ещё предстоит добавить.

## D012 · 2026-11-09 · Отдельная очередь обучения

Задания `agent.training` направляются в `dialogentis.training`, остальные — в `dialogentis.jobs`. Значение очереди хранится в Job и outbox; проверка типа задания и составной внешний ключ не допускают несовпадения. Диспетчер видит только outbox, проверяет подтверждения публикации обоих брокеров и не может менять очередь или tenant. Worker при захвате повторно проверяет очередь, поэтому сообщение с корректными UUID в чужой очереди не изменяет задание. Retry и восстановление сохраняют прежнюю маршрутизацию.

В Compose отдельный training-worker запущен с одним Taskiq-процессом и лимитами 2 CPU/4 GiB. Миграция 0012 в одной транзакции переносит существующие события, временно снимая FORCE RLS только на время обновления владельцем таблиц и восстанавливая его до завершения миграции. Обработчик и глобальная блокировка обучения описаны в D014.

## D011 · 2026-11-09 · Внутренние подписанные NLP-модели

Модель создаётся только внутренним кодом обучения и хранится в приватном ArtifactStorage как артефакт типа `model`; пользовательский импорт моделей запрещён. Сериализация использует pickle, который допускает выполнение кода при загрузке. До десериализации проверяются HMAC-SHA256 с ключом, полученным из `ENCRYPTION_KEY` с отдельным назначением, UUID организации, агента, версии и артефакта, SHA-256, версия ключа, версия реализации NLP и точные версии Python/Pydantic/NumPy/SciPy/scikit-learn/python-crfsuite/google-re2. Несовместимый или изменённый артефакт отклоняется. Сервисам, вызывающим упаковку, нельзя передавать загруженные пользователем объекты; они обязаны предварительно проверить права и принадлежность версии организации. Подпись не защищает от компрометации ключа или доверенного процесса-подписанта.

Лимит одного модельного файла задаётся отдельно от общей квоты, поэтому уменьшение квоты не отключает уже созданные модели. Потеря или смена ключа без сохранения старого делает модели недоступными; безопасную ротацию и поддержку старого keyring ещё нужно реализовать до такой операции. При обновлении версий библиотек старые артефакты отклоняются, пока не будет предусмотрен совместимый переход. Политика восстановления и развёртывания должна учитывать оба ограничения.

## D010 · 2026-11-09 · CRF и объединение сущностей

Для learned-сущностей используется python-crfsuite с BIO-метками UUID и тем же токенизатором, что проверяет разметку. В обучение входят все train-фразы, включая последовательности без сущностей; test-фразы не участвуют. CRF использует признаки текущего и соседних токенов, LBFGS и фиксированные параметры, записанные в manifest. Временный файл модели создаётся в приватном каталоге и после чтения удаляется; результат пока находится только во внутреннем объекте. Загрузка произвольных моделей пользователем не предусмотрена. Для каждой операции распознавания создаётся отдельный Tagger, поскольку он изменяет внутреннее состояние.

При объединении сначала выбираются regex, затем словари и learned; в каждой группе более длинное совпадение имеет приоритет, при равной длине — меньший UUID. Словарь передаёт все пересекающиеся кандидаты: отклонение длинного совпадения из-за regex не скрывает непересекающийся короткий вариант. Причина отклонения сохраняется с перекрывшим кандидатом. Если кандидатов больше 10000 на сообщение, операция завершается ошибкой вместо молчаливого усечения. Это защитная граница, требующая нагрузочной проверки. Точность сущностей считается по UUID и точным code-point границам. Ошибка преобразования значения считается отдельно; проверка равенства нормализованному эталону пока невозможна, поскольку эталонное значение не хранится в разметке.

## D009 · 2026-11-09 · Классификатор намерений и held-out метрики

Для word и char_wb TF-IDF выделено по 25000 признаков, затем объединённый вектор нормализуется по L2 и подаётся в LogisticRegression. Word-токенизатор учитывает отдельные небуквенные символы, чтобы допустимый набор из emoji или знаков не приводил к пустому словарю. Для максимального cosine similarity сохраняются нормализованные векторы только включённых train-примеров. Seed, версии Python/Unicode/NumPy/SciPy/scikit-learn и существенные параметры сохраняются в manifest; SHA-256 от упорядоченных пар intent UUID и train-текста проверяется при оценке, test-тексты в него не входят. Это только hash входа классификатора, не полный nlu_hash и не безопасный формат хранения моделей.

Для метрик матрица содержит отдельную строку и столбец fallback. Ошибочно принятые unknown учитываются как false positive соответствующего намерения, ошибочный fallback известной фразы — как false negative. Средние считаются только по определённым значениям; при отсутствии наблюдений результат null, а отключённые намерения исключаются и явно считаются отдельно. Score модели не объявляется гарантированной вероятностью правильности.

## D008 · 2026-11-03 · Транзакционный outbox и роль диспетчера

Job и outbox создаются в транзакции tenant и защищены RLS; составной FK не допускает ссылку события на Job другой организации. Job хранит UUID организации без внешнего ключа на неё, чтобы состояние удаления могло пережить удаление tenant. Создающий задание сервис обязан до вызова проверить существование организации и членство.

Диспетчер использует отдельную роль с доступом только к служебному outbox и правом изменять `published_at`; данные организаций и Job ей недоступны. Одноразовый Compose-сервис создаёт эту роль через bootstrap-подключение и сохраняет случайный пароль в отдельном volume. API не получает bootstrap-пароль и volume диспетчера. Отправка подтверждается брокером до фиксации `published_at`. При потере подтверждения сообщение может быть доставлено повторно; идемпотентный worker и восстановление ещё предстоит реализовать до включения пользовательских задач.

## D005 · 2026-10-30 · Compose и сеть

PostgreSQL 18.4, RabbitMQ 4.2, Python, Node 24 LTS, Caddy и Mailpit закреплены digest. Node 24 принят для воспроизводимой сборки фронтенда. Внутренняя сеть БД/broker закрыта, сетевой выход есть только у HTTP/SMTP компонентов. API получает только runtime-переменные; bootstrap и migration credentials туда не передаются. Локальные порты 18000/18080/18025 выбраны из-за занятого другим приложением порта 8000. Параметр PUBLIC_BASE_URL согласован с 18080.

## D006 · 2026-10-30 · Доставка auth-писем

Письма подтверждения, восстановления и приглашения сохраняются атомарно с токеном в зашифрованный PostgreSQL email outbox. Отдельный процесс читает его с SKIP LOCKED, отправляет через стандартный smtplib и удаляет payload после подтверждения SMTP; временные ошибки сохраняют ограниченный backoff. Это самостоятельный узкий механизм для auth-писем, не готовая реализация Job/outbox для обучения на S06. Доставка at-least-once, ссылки одноразовые. При смене ключа надо предварительно опустошить очередь; keyring ещё не реализован.

## D007 · 2026-10-30 · Контракты и сессии

Error envelope приведён к ТЗ: request_id находится внутри error; заголовок X-Request-ID остаётся. ETag использует `"rev-N"`. Открытые auth-операции проверяют Origin; операции с cookie также требуют CSRF HMAC, привязанный к session token. Сессии непрозрачные, хранятся хешированными, имеют idle/absolute expiry. Транзакционная dependency завершается до отправки ответа, чтобы ошибка commit не выдавала клиенту успешный результат. Auth rate limits сериализуются advisory lock в PostgreSQL, не зависят от числа API-процессов. Для dev origins явно перечислены локальные порты; в production исключений нет.

Контейнер API доступен только на loopback и доверяет Caddy forwarded headers для определения адреса клиента. Вынос API на публичный адрес потребует ограничения доверенных proxy. Тестовый контур выделен в `dialogentis-test` и не пишет аккаунты в development-БД. Индекс гарантирует максимум одного владельца; запрет удаления последнего владельца обеспечен сервисом. Перевод ownership выполняется в транзакции под блокировкой организации.
