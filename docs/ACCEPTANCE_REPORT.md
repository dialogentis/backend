# Приёмка первого выпуска Dialogentis

Приёмка S15 продолжается. В журнале этапов сохранены результаты прогонов и найденные ограничения. Все команды для локальной проверки выполняются на отдельном Compose-проекте с отдельными томами PostgreSQL, RabbitMQ, Mailpit и артефактов.

## Воспроизведение

- Совместная проверка. Из backend после первого запуска `CHROME_PATH=/absolute/path/to/chromium make acceptance` проверяет оба репозитория и запускает инсталляцию для браузерных сценариев на свободных портах 18100, 18125 и 18180.
- Сервер и контракт. Из backend запустите `make integration`. Для вспомогательных проверок используются `uv run --locked ruff check`, `uv run --locked ty check` и генерация OpenAPI из `scripts/export_openapi.py`. Команды CI описаны в [.github/workflows/backend.yml](../.github/workflows/backend.yml).
- Кабинет и контракт клиента. Из frontend запустите `npm ci`, `npm run typecheck`, `npm run test:unit`, `npm run build` и `npm run api:generate`. Сценарии Chrome с реальной базой и очередью описаны в [инструкции frontend](../../frontend/README.md#проверки).
- Развёртывание, резервное копирование и восстановление. Используйте [инструкцию эксплуатации](OPERATIONS.md) и раздел Production в [README](../README.md#production).
- Производительность и обучение. Команды и форматы результатов описаны в [нагрузочном сценарии](../benchmarks/runtime/README.md) и [сценарии проверки качества](../benchmarks/nlu/README.md#демонстрационные-агенты-выпуска).

В итоговом локальном прогоне Linux Compose прошёл 361 серверный тест за 90,53 с. Ruff, ty и проверка OpenAPI прошли. На frontend `c762706` успешно завершились production-сборка, проверка контракта, типизация, три модульных теста и весь браузерный набор на чистом Compose-проекте. Результаты приведены в [журнале S15](IMPLEMENTATION_STATUS.md).

## Диагностика нагрузки на ARM64

Использованы Linux ARM64, 10 vCPU, 7,8 ГиБ RAM, Docker Engine 29.6.1 и Compose 5.3.0. Замер выполнен на серверной ревизии `f251462` с двумя процессами API. В десяти организациях обучены и опубликованы 100 моделей. У каждого активного агента пять намерений и 500 обучающих фраз. Каждый профиль держал 100 диалогов с десятью агентами при 10 отправках в секунду после двухминутного прогрева. [Результат замера](../benchmarks/runtime/results/2026-11-22-arm64.json), [сценарий и конфигурация стенда](../benchmarks/runtime/README.md).

- **Без обучения.** В 15-минутном окне успешны 8820 из 9000 сообщений. p50/p95/p99 успешных ответов — 65,5/101,1/208,1 мс. При прогреве два хода исчерпали лимит в 20 секунд. PostgreSQL зафиксировал неизвестный исход в двух диалогах, последующие запросы к ним дали 180 ответов HTTP 409. Все 900 GET кабинета успешны, p50/p95/p99 — 30,7/42,0/271,1 мс.
- **С обучением.** Все 9000 сообщений и 900 GET кабинета успешны. p50/p95/p99 ответов — 67,0/125,8/309,1 мс, GET — 23,5/54,6/274,6 мс. В основном окне наблюдалась 381 задача, выполнялись последовательно по одной. Нижняя оценка времени в состоянии `running` — 482 секунды из 900.
- **Холодные модели и сохранения.** Все 90 холодных моделей ответили, p50/p95/p99 — 56,7/81,8/1498,4 мс. На 20 сохранениях по 1 048 545 и 10 485 729 байт ошибок не было. p50/p95/p99 — 82,5/93,6/95,4 и 785,4/899,4/966,6 мс соответственно.
- **Ресурсы.** В 128 базовых выборках средний и пиковый CPU API составили 54,4% и 110,6%, максимальная RAM — 1651 МиБ. В 129 выборках с обучением API использовал 55,9% и 124,2% CPU, до 1661 МиБ RAM. PostgreSQL в этом окне использовал 24,2% и 77,8% CPU, до 196 МиБ RAM. У процесса обучения зафиксированы 70,3% и 112,0% CPU, до 454 МиБ RAM. За 100% CPU принят один vCPU.

Полученные задержки укладывались в численные пороги ТЗ. Конфликты после прогрева стали причиной ограничения очереди ожидания слотов и повторной проверки.

В коротком повторе на ревизии `1adec33` успешны все 1200 сообщений прогрева и все 600 сообщений минутного окна. p50/p95/p99 в окне — 44,1/55,0/93,8 мс, p95 на 60 GET кабинета — 37,2 мс.

### Полный повтор после исправления

23 ноября на том же Linux ARM64 повторены оба окна на серверной ревизии `70fd186` с двумя процессами API и одним процессом обучения. Два прогрева по 120 секунд прошли по 1200 сообщений без ошибок. В каждом 15-минутном окне поддерживалось 100 активных диалогов при 10 сообщениях в секунду. [Полный отчёт с ресурсами](../benchmarks/runtime/results/2026-11-23-arm64-fixed.json), [команды и состав данных](../benchmarks/runtime/README.md).

- **Без обучения.** Доставлены 9000 из 9000 сообщений, p50/p95/p99 — 42,8/49,5/75,5 мс. Все 900 GET кабинета успешны, p50/p95/p99 — 18,9/29,3/34,9 мс.
- **С обучением.** Доставлены 9000 из 9000 сообщений, p50/p95/p99 — 41,5/55,4/87,8 мс. Все 900 GET кабинета успешны, p50/p95/p99 — 18,8/27,9/125,9 мс. Наблюдалась 491 последовательная задача обучения. Нижняя оценка суммарного времени в состоянии `running` — 313,7 секунды из 900.
- **Холодные модели и сохранения.** Все 90 холодных моделей ответили, p50/p95/p99 — 28,2/32,5/800,6 мс. Успешны все 20 сохранений черновика каждого размера. p50/p95/p99 для 1 048 545 байт — 92,6/123,2/128,6 мс, для 10 485 729 байт — 816,6/1085,1/1319,0 мс.
- **Ресурсы.** В 128 базовых выборках API использовал в среднем 28,7% одного vCPU, в пике 46,6%, до 1041,4 МиБ RAM. В 129 выборках с обучением API использовал 31,8% и 52,4% CPU, до 1052,7 МиБ RAM. В том же окне процесс обучения использовал 51,6% и 94,3% CPU, до 463,9 МиБ RAM. По всем контейнерам средний и пиковый CPU и пиковая память включены в JSON.

На ARM64 выполнены пороги задержки и ошибок NFR-01/02. Подтверждение на целевом Linux x86-64 остаётся открытым.
