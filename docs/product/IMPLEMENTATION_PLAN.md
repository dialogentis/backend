# План последовательной реализации Dialogentis

Версия 1.3. Дата 30 октября 2026 года.

План предназначен для агента, который реализует платформу целиком в существующей рабочей области. Он исполняется последовательно. Источник функциональных требований — `TECHNICAL_SPECIFICATION.md`; данный план задаёт порядок, результаты и проверки, не сокращая состав первого выпуска. Рабочая документация ведётся в Markdown; генерировать или обновлять Word/PDF в процессе разработки не требуется.

## 1 Правила исполнения

1. Перед началом прочитать ТЗ, этот план, локальные AGENTS.md, актуальные README и `IMPLEMENTATION_STATUS.md`, если он уже создан. Проверить status и remotes отдельно в frontend и backend. Сохранить чужие незакоммиченные изменения; не создавать родительский Git-репозиторий и не удалять вложенные `.git`.
2. Выполнять этапы S01–S16 по порядку. Внутри этапа сначала зафиксировать модели/контракт и проверки, затем реализовать сервер и интерфейс, затем подтвердить интеграцию. У предыдущих этапов могут появляться новые проверки, если их поведение меняется.
3. Не останавливаться после прототипа, красивого UI, списка TODO или сгенерированных таблиц. Запрос пользователя охватывает весь первый выпуск. Разрешены обычные обратимые действия разработки и локальные проверки; живые домены/секреты не выдумывать и реальную публикацию во внешнюю инфраструктуру без доступной конфигурации не считать выполненной.
4. Не заменять рабочую функциональность mock-данными. Mock допустим только для внешнего HTTP-сервиса и почтовой доставки в локальных/e2e-тестах. Кабинет, обучение, публикация, виджет и аналитика работают с реальным API и БД.
5. Обычные технические решения принимать самостоятельно в рамках ТЗ и фиксировать в DECISIONS.md. При непредвиденной несовместимости сначала исследовать и найти минимальное решение; не менять согласованные роли, каналы или правила изоляции для удобства реализации.
6. После этапа обновлять IMPLEMENTATION_STATUS.md: результат, точные команды и результат проверок, изменённые миграции/контракты, оставшиеся дефекты и следующий этап. Нельзя ставить completed при упавшей обязательной проверке. Проверка, которую не удалось выполнить, отмечается как not_run с причиной, а не как passed.
7. На ошибке исправлять первопричину и повторять затронутые проверки. Переходить к независимой части работы можно, но не закрывать этап, пока его exit criteria не выполнены. Для отсутствующего production SMTP/domain продолжать полную локальную реализацию; отдельно перечислить обязательную конфигурацию оператора.
8. Секреты, реальные письма пользователям, изменение сторонних систем и production-деплой не являются способом проверки локальной функции. Для интеграционного сценария использовать изолированные тестовые данные и заранее определённый mock-service.

## 2 Результаты и журнал

К концу разработки должны существовать frontend и backend, воспроизводимый Compose, миграции, OpenAPI, generated client, тесты, демонстрационные агенты, инструкция эксплуатации и отчёт приёмки AC-01–AC-14. Список выполненных файлов без работающего сценария недостаточен.

Журнал должен иметь поля: stage, status `pending|in_progress|completed|blocked`, started_at, completed_at, changed_paths, checks, decisions, blockers, next_step. Статус blocked используется для конкретного внешнего препятствия с описанием, какая независимая работа продолжена; он не означает готовность продукта. Одновременно основной in_progress этап один.

DECISIONS.md содержит номер решения, дату, вопрос, выбранное решение, основание и последствия. ACCEPTANCE_REPORT.md содержит соответствие AC/NFR, стенд, команды, результаты и ссылки на отчёты тестов. Секреты и исходный текст реальных разговоров в этих документах запрещены.

## S01 Проверка окружения и основание репозиториев

Вход: текущие frontend/backend и согласованное ТЗ.

- Проверить Git-статус обоих репозиториев, существующие файлы и инструкции. Не предполагать наличие CI, доступа к registry или GitHub.
- Создать каркас frontend на React/TypeScript/Vite и backend на Python 3.14/FastAPI. Сначала подтвердить Linux-установку совместимого набора scikit-learn, python-crfsuite и безопасного regex-движка, например google-re2. Использовать стандартный CPython с GIL. Закрепить выбранные версии, Node LTS и образы; записать архитектурные решения. Ветку Python 3.14 не понижать для обхода несовместимости зависимости.
- Для фронтенда настроить package manager с lock-файлом. Для бэкенда использовать uv: создать `pyproject.toml` с `requires-python = ">=3.14,<3.15"`, `.python-version` с веткой 3.14 и `uv.lock`. В dev-группу включить Ruff, ty и pytest. Настроить Ruff для форматирования/линтинга и ty для проверки типов под Python 3.14. Docker и CI устанавливают зависимости через uv по тому же lock-файлу; отдельный lock и Docker build у каждого приложения.
- Для фоновых задач закрепить Taskiq и taskiq-aio-pika в runtime-зависимостях uv. Проверить установку на Python 3.14 и smoke-постановку/обработку задачи через реальный RabbitMQ; проверить поддержку ручного ack и publisher confirms выбранным адаптером.
- Создать backend/compose.yaml с соседним frontend build context и профилями dev/test, healthchecks, закрытой сетью БД/broker и Mailpit. Сразу добавить env validation без рабочих секретов.
- Поместить версионируемые копии Markdown-документов в backend/docs/product, добавить ссылки в README обоих репозиториев с учётом реального remote. Общий docs оставить доступным как исходник и указатель запуска. Старую Word-копию не включать в актуальную документацию и не обновлять.
- Создать журнал исполнения и базовые CI-команды; production-образы пока могут показывать health/start page, но не считаться функциями продукта.

Проверки: `uv sync --locked`; версия `uv run --locked python --version` соответствует 3.14.x; `uv run --locked ruff format --check .`; `uv run --locked ruff check .`; `uv run --locked ty check`; `uv run --locked pytest`; train/predict smoke для intent/CRF; безопасное отклонение недопустимого regex; backend health; frontend build/typecheck; Compose config и старт. Проверить production-установку через `uv sync --locked --no-dev`. После этого S01 завершён.

## S06 Очереди задания и артефакты

Зависимость: S05. Этот этап подключает проверенные функции импорта/экспорта к очереди и интерфейсу.

- Реализовать Job, OutboxEvent, dispatcher, Taskiq tasks через taskiq-aio-pika, heartbeat, отмену, timeout и terminal states. Payload broker содержит только проверенные идентификаторы и служебные поля. Durable queue/persistent messages и publisher confirms обязательны; published_at сохраняется после подтверждения публикации.
- Разделить обычные задачи и обучение по очередям и отдельным Taskiq workers. CPU-обучение запускать в управляемом дочернем процессе training worker с возможностью завершения по отмене/таймауту; heartbeat не должен останавливаться на вычислениях. Состояние Job — в PostgreSQL, ограничение параллелизма — явное и проверяемое.
- Настроить manual ack после фиксации результата/повтора в БД. Повторами управляет Job/outbox с ограничением попыток, backoff и jitter; автоматический retry middleware Taskiq отключён, чтобы не создавать второй цикл повторов. Терминальные, отменённые и ошибочно сконфигурированные Job не исполняются заново. Добавить dead-letter queue для poison messages.
- Запустить один TaskiqScheduler с LabelScheduleSource для периодических задач; дедупликация запуска — через PostgreSQL. Динамические повторы идут через next_retry_at в outbox. Проверить выполнение просроченной очистки после восстановления scheduler; не добавлять Redis для расписаний.
- Реализовать private ArtifactStorage с safe path, checksum, атомарным finalize, квотой и TTL для временных файлов. Артефакты разных организаций не смешиваются.
- Подключить import preview, атомарный apply по исходному revision и export к API/UI. Перевести письма и cleanup на надёжные задания. Сделать универсальный frontend progress panel с корректным polling.
- Реализовать reconciliation зависших jobs после потери worker/broker; повторная доставка не создаёт вторую логическую операцию.

Проверки: перезапуск broker/worker/API/scheduler; падение worker до ack и после commit; ошибка БД перед ack; повторная доставка; повторная публикация после потери подтверждения; отсутствие двойного логического выполнения; работа heartbeat при CPU-нагрузке; отмена queued/running и завершение дочернего процесса; bounded retry/dead-letter; дедупликация периодических задач; доступ к чужому артефакту, TTL download и квота. Полностью пройти AC-04 через import/export UI/API, включая устаревший preview и отсутствие частичной записи. Exit: импорт/экспорт работают насквозь, нет бессрочных running или «потерянных успешных» задач после перезапуска.
