# Техническое задание на разработку Dialogentis

Версия 1.3. Дата 30 октября 2026 года.

Dialogentis — веб-платформа, в которой организации создают, обучают, проверяют и публикуют специализированных чат-ботов. Пользователь задаёт намерения, размечает сущности и собирает сценарии в визуальном редакторе. Опубликованный бот работает через чат на сайте или HTTP API. Организации используют общую установку платформы, но имеют изолированные данные, участников, агентов и секреты.

Этот документ определяет поведение фронтенда, бэкенда и среды исполнения. Последовательность реализации и критерии завершения этапов находятся в `IMPLEMENTATION_PLAN.md`. Точка входа для реализующего агента — `START_HERE.md`. ТЗ, план, решения и журнал реализации ведутся в Markdown и являются актуальными источниками для разработки. Ранее подготовленная Word-версия остаётся исторической копией и больше не синхронизируется; при расхождении использовать Markdown.

## 1 Границы продукта и принятые решения

### 1.1 Обязательный состав первого выпуска

- Несколько организаций; один пользователь может состоять в нескольких организациях. Самостоятельная регистрация, создание организаций и приглашения по почте.
- Вход по почте и паролю, подтверждение почты, восстановление пароля и выход из всех сеансов.
- Роли владельца, администратора, редактора и наблюдателя; серверная проверка доступа к каждому действию.
- Агенты на русском языке; намерения, сущности, обучающие примеры и независимые тестовые наборы.
- Визуальные сценарии: ответы, условия, сбор параметров, HTTP-действия, передача другому агенту и возврат.
- Обучение в фоне, отчёты о качестве, тестовый чат с трассировкой, неизменяемые версии, публикация и откат.
- Встраиваемый чат для сайта и внешний HTTP API; управление ключами и разрешёнными сайтами.
- История диалогов, техническая диагностика и базовая аналитика организации.
- Русский интерфейс, светлая и тёмная темы; адаптивный кабинет, редактор графа для компьютера.
- Развёртывание на Linux через Docker Compose, локальная среда разработки, миграции, резервное копирование и проверяемое восстановление.

### 1.2 Следующие версии

Генерация ответов языковой моделью, поиск по загруженным документам, Telegram, SSO, оплата и тарифы, исполнение пользовательского Python/JavaScript, совместное редактирование в реальном времени и бизнес-воронки не входят в первый выпуск. Архитектура должна позволять заменить NLP-механизм через внутренний интерфейс, но реализация этих функций не является условием приёмки.

### 1.3 Основания решений

Функциональный объём согласован в ответах владельца проекта. Следующие инженерные решения задаются этим ТЗ: конкретный стек, типы блоков, лимиты, API, структура версий, алгоритмы NLP, сроки технических токенов и целевые показатели. Их следует реализовать как описано; изменения фиксировать в `docs/DECISIONS.md` с причиной и влиянием на API, данные и проверки. Несовместимое изменение согласованного поведения нельзя оформлять как внутренний рефакторинг.

Срок разработки не фиксируется. План предназначен для последовательного исполнения агентом до готовности всех функций первого выпуска. Промежуточные этапы дают работающие части платформы, но не сокращают итоговый объём.

## 2 Технологии и общая архитектура

### 2.1 Фронтенд

Использовать React, TypeScript в строгом режиме и Vite. Кабинет является SPA; серверный рендеринг для закрытого рабочего интерфейса не требуется. React Router отвечает за маршруты, TanStack Query — за серверные данные, React Hook Form и Zod — за формы. Клиент API и типы генерируются из OpenAPI бэкенда. Локальное состояние редактора хранится в Zustand; серверные данные не дублируются в глобальном хранилище.

Граф строится на `@xyflow/react` — React Flow. Компоненты интерфейса использовать на базе shadcn/ui и Tailwind CSS с общей системой цветовых токенов. Иконки — Lucide. Даты отображаются через Intl; тексты интерфейса вынесены из компонентов в русский словарь. Не добавлять второй набор компонентов или второй механизм управления серверным состоянием.

Виджет собирается отдельной точкой входа того же фронтенд-репозитория: небольшой загрузчик открывает iframe с чатом на домене платформы. CSS кабинета и сайта заказчика не должен влиять на содержимое iframe.

### 2.2 Бэкенд

Использовать Python 3.14, FastAPI, Pydantic, SQLAlchemy 2 и Alembic. Основной сервер — модульный монолит с модулями `auth`, `organizations`, `agents`, `datasets`, `nlu`, `flows`, `training`, `testing`, `releases`, `runtime`, `channels`, `integrations`, `analytics`, `audit` и `jobs`. Границы модулей выражаются сервисами и схемами, а не отдельными сетевыми сервисами.

Обязательные инструменты бэкенда: uv для управления Python, виртуальным окружением и зависимостями; Ruff для линтинга и форматирования; ty для проверки типов. Конфигурация хранится в `pyproject.toml`, зависимости закреплены в `uv.lock`, ветка интерпретатора — в `.python-version`. Задать `requires-python = ">=3.14,<3.15"`; использовать стандартный CPython 3.14 с GIL, а не free-threaded сборку. Конкретный patch-релиз закрепляется при реализации в образах и CI.

Ruff настраивается на Python 3.14; ty проверяет типы приложения, workers и тестов в окружении uv с Python 3.14. Ruff, ty и pytest входят в группу dev зависимостей проекта. Локальные команды, Docker и CI используют один `uv.lock`; установка для разработки — `uv sync --locked`, для production — `uv sync --locked --no-dev`. Форматирование выполняется через `uv run --locked ruff format .`, проверки — через `uv run --locked ruff format --check .`, `uv run --locked ruff check .`, `uv run --locked ty check` и `uv run --locked pytest`. Миграции запускаются через `uv run --locked alembic upgrade head`. В production команды запуска и миграций также передают `--no-dev`, чтобы uv run не устанавливал dev-инструменты. Не вводить второй менеджер зависимостей, форматтер или проверяющий типы инструмент вместо согласованных.

PostgreSQL хранит пользователей, конфигурации, состояния диалогов, задания, аудит и агрегаты. Taskiq с RabbitMQ выполняет обучение, пакетное тестирование, импорт, экспорт, доставку писем и очистку. Подключение RabbitMQ — через `taskiq-aio-pika`. Taskiq и этот адаптер входят в runtime-зависимости uv; их совместимость с Python 3.14 проверяется на S01. Статусы и результаты заданий хранятся в PostgreSQL в прикладных Job/Artifact; отдельное хранилище результатов Taskiq не требуется. RabbitMQ не является источником истины. Redis в первом выпуске не требуется: аренды редактирования и сериализация диалогов реализуются через PostgreSQL.

Обучение выносится из процесса API. Внутренние BackgroundTasks FastAPI не использовать для операций, которые должны переживать перезапуск сервера. Задания публикуются через transactional outbox. Диспетчер выбирает готовые записи outbox с блокировкой и передаёт в Taskiq только проверенные job_id и organization_id. Публикация использует durable queues, persistent messages и publisher confirms; published_at записывается после подтверждения брокера. Повторная доставка безопасна благодаря идемпотентности обработчиков.

Для workers Taskiq использовать ручное подтверждение `ack_type=manual`: обработчик вызывает Context.ack только после фиксации terminal status или надёжной постановки повтора в PostgreSQL/outbox. Раннее подтверждение при получении запрещено. При ошибке фиксации БД сообщение остаётся неподтверждённым; обработчик закрывает/восстанавливает consumer channel для повторной доставки. На S06 проверить именно эту последовательность на реальном RabbitMQ и закреплённых версиях библиотек.

Повторами управляет один прикладной механизм Job/outbox; параллельные автоматические повторы через Taskiq retry middleware отключены. Временные инфраструктурные ошибки обычных идемпотентных задач допускают до трёх повторов с exponential backoff и jitter; ошибки конфигурации, отмена и terminal Job не повторяются. Источник времени следующей попытки — next_retry_at в outbox. Потеря worker обучения обрабатывается по правилам раздела 8, без автоматического запуска второй тренировки. Poison messages направляются в dead-letter queue с ограниченным числом доставок и диагностикой; бесконечного немедленного requeue нет.

TaskiqScheduler с LabelScheduleSource запускается одним экземпляром для периодической очистки, сверки jobs и обслуживания retention. Дедупликация периодического задания по имени и временному интервалу обеспечивается PostgreSQL. Динамические повторы идут через outbox; Redis для schedule source не добавляется. При остановке scheduler после восстановления выполняется проверка просроченных очисток и зависших jobs.

### 2.3 NLP и управление диалогом

Начальная реализация NLP: scikit-learn для классификации намерений, python-crfsuite для обучаемого извлечения сущностей, словари и ограниченные регулярные выражения для явно заданных сущностей. Управление диалогом — собственный детерминированный интерпретатор типизированного графа. Rasa не является обязательной зависимостью.

Причина выбора: интерфейс платформы должен управлять жизненным циклом, версиями, передачей контекста и трассировкой. Разделение NLP и интерпретатора делает эти правила явными. Классические модели здесь являются начальным способом распознавания, качество которого проверяется на независимых наборах; они не гарантируют понимание произвольной фразы.

Контракт NLP состоит из `validate_dataset`, `train`, `evaluate`, `load` и `predict`. Результат predict содержит ранжированные намерения со score, сущности с позициями и источником извлечения, причины fallback и версию модели. Реализация интерпретатора не должна зависеть от классов scikit-learn.

### 2.4 Инфраструктура и зависимости

Docker Compose запускает reverse proxy Caddy, статический фронтенд, API, Taskiq worker для обычных задач, отдельный Taskiq worker обучения, TaskiqScheduler, outbox dispatcher, PostgreSQL и RabbitMQ. Workers слушают разные очереди; обычные фоновые операции не ждут обучения. CPU-обучение выполняется в управляемом дочернем процессе training worker, чтобы не блокировать его event loop и heartbeat; отмена/таймаут завершают дочерний процесс с очисткой ресурсов. Одного объявления тяжёлой функции как async недостаточно. Mailpit включается только в профиль разработки. На production SMTP задаётся переменными окружения. Бинарные модели, архивы и временные экспорты хранятся в приватном файловом volume через интерфейс ArtifactStorage; API и workers видят один volume. Прямой доступ reverse proxy к нему запрещён.

PostgreSQL использовать из поддерживаемой стабильной ветки; базовый выбор — 18. На этапе S01 выбрать поддерживаемую LTS-ветку Node.js, совместимую с выбранным Vite, и закрепить её. Версии Python-пакетов закрепить через uv в `uv.lock`, npm-пакетов — lock-файлом фронтенда, Docker-образов — тегами с digest; не использовать `latest` в production. Совместимость Python 3.14, scikit-learn, python-crfsuite и выбранной обёртки RE2 подтвердить установкой и небольшим train/predict внутри Linux-контейнера до разработки доменных функций. Точные версии uv, Ruff, ty, Python и библиотек записать в DECISIONS.md. При несовместимости зависимости сначала подобрать совместимый релиз или реализацию адаптера; не понижать согласованную ветку Python без отдельного решения владельца проекта.

## 3 Организации и права

### 3.1 Изоляция и структура

Организация является рабочим пространством и границей данных. В первом выпуске дополнительного уровня «проект» нет: организация содержит агентов, интеграции, участников, каналы, диалоги и отчёты. Пользователь имеет глобальный аккаунт и отдельное membership в каждой организации. Активная организация задаётся URL и не меняет права в других организациях.

Каждая принадлежащая организации запись содержит `organization_id`. Все запросы, фоновые задания, кэш моделей, файловые пути и выгрузки учитывают этот идентификатор. Составные внешние ключи `(organization_id, resource_id)` исключают ссылки между организациями. Сервер не доверяет organization_id в теле запроса без проверки членства.

Для таблиц организации включить PostgreSQL RLS. Рабочая роль БД не является владельцем таблиц, superuser или BYPASSRLS. Контекст организации задаётся через transaction-local `set_config`; при отсутствии контекста доступ запрещён. Для каждого запроса и каждого задания создаётся новая транзакция с контекстом. Роль миграций отделена от роли приложения. Глобальные аккаунты и membership обслуживаются ограниченными auth-сервисами; публичный runtime получает организацию только из проверенного канала или ключа. RLS дополняет проверки сервиса, а не заменяет их.

### 3.2 Роли

- Владелец: все права организации, передача владения, удаление организации и управление администраторами. У организации ровно один владелец.
- Администратор: участники кроме смены владельца, настройки организации, секреты, каналы, ключи API, публикация и откат, все права редактора; экспорт и удаление истории.
- Редактор: создание и изменение агентов, разметка, обучение, тесты, диагностика и просмотр истории/аналитики. Не управляет участниками, секретами, публикацией, ключами, экспортом и массовым удалением истории. Может выбрать существующую интеграцию по имени, не получая её секрет.
- Наблюдатель: чтение конфигураций, отчётов, истории и аналитики; тестовый чат с готовой версией. Не сохраняет изменения, не запускает обучение/пакетные тесты и не вызывает реальные HTTP-действия в тестовом чате.

Разрешение проверять на сервере и отражать в интерфейсе: недоступное действие скрыто либо заблокировано с объяснением. Пользователь вне организации получает 404 на её ресурсы, участник без права — 403. Изменение роли применяется к следующему запросу, а не после повторного входа.

### 3.3 Жизненный цикл организации

После подтверждения почты пользователь создаёт организацию с названием и уникальным slug, становится владельцем и попадает в пустой список агентов. Приглашение содержит организацию, email и роль; действует 7 дней, одноразовое, хранится как хеш токена. Получатель входит или регистрируется с тем же подтверждённым email. Повторный приём не создаёт второе membership. Администратор может отозвать приглашение или отправить новое.

Передача владения требует повторного ввода пароля, выбора существующего участника и атомарного изменения обеих ролей. Владелец не может выйти или быть удалён до передачи владения. Удаление организации требует пароля и ввода её названия; новые диалоги и задания сразу запрещаются. Очистка данных и артефактов выполняется заданием не позднее 24 часов; общие аккаунты пользователей не удаляются. Восстановление после удаления через интерфейс отсутствует. Штатного интерфейса глобального администратора платформы в первом выпуске нет.

## 4 Авторизация и защита сеансов

### 4.1 Пользовательские сценарии

AUTH-01: регистрация по email и паролю; пароль 12–128 символов, разрешены пробелы и Unicode. Пароль хешируется Argon2id. Ответ регистрации не раскрывает, зарегистрирован ли адрес. Подтверждение email действует 24 часа; повторная отправка ограничена частотой.

AUTH-02: до подтверждения email доступны только экран подтверждения, повторная отправка и выход. После подтверждения открывается создание или выбор организации. Вход и восстановление возвращают нейтральные ошибки без проверки существования email через UI.

AUTH-03: токен восстановления действует 30 минут, одноразовый, в БД хранится хеш; изменение пароля отзывает все действующие сеансы. Страница восстановления не отправляет токен сторонним сервисам, не логирует его и исключает передачу через Referer.

### 4.2 Технический контракт

Для кабинета использовать непрозрачный серверный session token в cookie `HttpOnly`, `Secure`, `SameSite=Lax`, Path=/; срок бездействия 7 дней, абсолютный срок 30 дней. При входе session id заменяется. На state-changing запросах с cookie обязательны CSRF-токен и проверка Origin. Кабинет и API размещаются на одном origin. Cookie не используется для публичного API или iframe-виджета. localStorage не содержит паролей, токенов и секретов.

Ограничения по умолчанию: 5 неуспешных входов за 15 минут на сочетание IP/email, 20 на IP; восстановление и повторная отправка подтверждения — 3 в час на адрес. Ответ 429 содержит Retry-After. Подсчёт не позволяет обойти лимит несколькими API-процессами. При logout сеанс удаляется; «выйти везде» отзывает все сеансы пользователя.

## 5 Агенты и совместное редактирование

### 5.1 Структура агента

Агент содержит UUID, организацию, уникальный внутри организации slug, название до 120 символов, описание до 2000 символов, язык `ru`, статус `active|archived`, черновик и список версий. Публикация относится к конкретному release, а не к изменяемому объекту агента. Агент без опубликованного release недоступен внешнему пользователю.

Создание формирует пустой черновик с блоками Start, SwitchIntent, Fallback и End. Копирование создаёт новый агент и новые внутренние UUID, переносит данные/граф, но не переносит историю, публикации, ключи, секреты и блокировку. Ссылки на существующие интеграции и готовые версии других агентов допустимы только внутри той же организации и показываются пользователю для проверки.

Архивация запрещает новые сеансы этого агента; уже начатые продолжают работу с закреплёнными версиями. Нельзя архивировать агента, который требуется текущему опубликованному release другого активного агента: сначала нужно изменить и перепубликовать зависимый release. Восстановление из архива не публикует новую версию автоматически. Физическое удаление агента не входит в первый выпуск; удаление всей организации очищает и агентов.

### 5.2 Черновик и аренда редактирования

Единица эксклюзивного редактирования — весь черновик агента: намерения, сущности, примеры, тестовые данные, граф и поведение. Один пользователь/вкладка получает аренду на 90 секунд и продлевает её раз в 30 секунд. Разные агенты редактируются параллельно. Вторая вкладка того же пользователя также открывается в режиме чтения.

Сервер выдаёт lease token и монотонный fencing counter. Каждый PUT черновика содержит этот токен, counter и If-Match с revision. Старый редактор после истечения аренды не может сохранить изменения, даже если вкладка снова получила сеть. Неверный If-Match возвращает 412; занятая или утраченная аренда — 423. Администратор может отозвать аренду с обязательной записью аудита. Смена роли/удаление участника немедленно делает продление и сохранение недоступными.

Автосохранение — через 1,5 секунды после изменения, не чаще одного запроса в секунду. Есть индикаторы «Сохранение», «Сохранено», «Нет соединения» и «Блокировка утрачена». До подтверждения сохранения обучение и публикация заблокированы. При потере сети изменения остаются в памяти вкладки; после утраты аренды доступен экспорт локального черновика без секретов, но не тихая перезапись серверной версии. Несохранённые изменения предупреждают о закрытии вкладки.

## 6 Обучающие данные и NLP

### 6.1 Намерения и примеры

DATA-01: намерение имеет UUID, стабильный code в формате `[a-z][a-z0-9_]{1,63}`, русское название, описание и флаг enabled. Code уникален в агенте. Пример содержит UUID, исходный text, intent_id либо `expected_fallback=true`, split `train|test`, список размеченных spans. Для train fallback-примеры не используются классификатором, но могут храниться только как test.

DATA-02: одна фраза относится к одному намерению; multilabel в первом выпуске отсутствует. После trim/Unicode casefold/свёртки пробелов дубликат внутри train или test запрещён. Попадание одинаковой фразы в train и test блокирует валидацию: тест должен быть независимым. Удаление намерения или сущности со ссылками требует сначала устранить ссылки; интерфейс показывает список зависимостей. Автоматического удаления блоков графа нет.

DATA-03: для обучения необходимо минимум два включённых намерения и пять train-примеров на каждое. При числе меньше десяти показывать предупреждение о недостатке данных. Максимум первого выпуска — 100 намерений, 10000 train-примеров и 3000 test-примеров на агента; текст примера 1–2000 Unicode code points, полный черновик до 10 MiB. Ошибки лимита сообщаются до постановки задания.

### 6.2 Сущности и разметка

Сущность имеет UUID, code, название, тип результата `string|integer|number|boolean|date`, метод `learned|dictionary|regex`. Даты возвращаются в ISO 8601; неоднозначная дата не угадывается. Для dictionary задаются канонические значения и синонимы; для regex — шаблон и группа извлечения. Регулярные выражения выполняются движком с гарантированным ограничением времени/безопасным подмножеством, например RE2; backreferences и конструкции, которых нет в выбранном движке, отклоняются при сохранении. Выбор конкретной Python-обёртки RE2 подтвердить на S01; нельзя выполнять недоверенные шаблоны стандартным re без защиты от зависания.

Разметка — полуоткрытые интервалы `[start,end)` по Unicode code points в исходной строке, без NFC-преобразования текста перед сохранением. Фронтенд явно переводит индексы DOM/UTF-16 в code points и обратно. Проверять, что text[start:end] соответствует размеченному фрагменту; emoji, переносы и комбинируемые символы входят в тесты. Перекрывающиеся и вложенные сущности запрещены; допускается несколько непересекающихся вхождений одной сущности.

Для learned используется токенизация с сохранением позиций исходного текста и BIO-разметка CRF. Разметка должна совпадать с границами токенов, иначе UI предлагает расширить выделение, а сервер возвращает 422. Для каждого learned-типа необходимо не менее пяти размеченных train-вхождений; меньше десяти — предупреждение. Если learned-сущностей нет, CRF не обучается. Примеры без сущностей участвуют как отрицательные последовательности.

Совпадения объединяются по детерминированному приоритету: regex, затем dictionary с самым длинным совпадением, затем learned. При равенстве длины побеждает меньший стабильный UUID. Отклонённые пересечения отражаются в трассировке без изменения исходного текста. Нормализованное значение и исходный span хранятся раздельно.

### 6.3 Классификация и fallback

Начальный pipeline намерений: объединение word TF-IDF с ngram_range=(1,2) и char_wb TF-IDF с ngram_range=(3,5), затем LogisticRegression. Конкретные параметры, seed=42, нормализация и версии библиотек записываются в manifest модели. Ограничить суммарный словарь 50000 признаков. Test-примеры не участвуют в fit векторизатора или классификатора.

Значение score — оценка выбранной модели, а не гарантированная вероятность правильности. Начальные настраиваемые пороги: top score 0,55 и разница между первым и вторым score 0,15. Нулевой вектор всегда вызывает fallback. Дополнительно использовать максимальное cosine similarity к train-примерам, начальный порог 0,20; результат ниже порога — fallback. Пороги меняются в черновике, входят в версию и проверяются на test-наборе; отсутствие смысловой близости нельзя компенсировать только высоким score.

Причины fallback: `empty_features`, `low_score`, `ambiguous_intent`, `low_similarity`. Если несколько причин, вернуть все и выбрать первую в этом порядке как основную. Неизвестный запрос не запускает случайную ветку намерения. Ответ fallback настраивается в графе; после трёх подряд неудач бот предлагает пример допустимого запроса и завершение/перезапуск диалога.

### 6.4 Импорт и экспорт

Поддержать CSV UTF-8 и JSON с `schema_version=1`. CSV содержит `text,intent,split,entities`; entities — JSON-массив `{entity,start,end}` в экранированной CSV-ячейке. JSON содержит определения намерений/сущностей и массив examples. Максимальный файл 10 MiB. Импорт имеет preview: ошибки со строкой и полем, новые/существующие коды, дубликаты и ожидаемое число изменений. Применение требует lease и If-Match; если черновик изменился после preview, нужен повторный preview.

Режимы merge и replace задаются явно; по умолчанию merge без молчаливой перезаписи совпадающих UUID/кодов. Любая ошибка блокирует весь apply; частично импортированный набор не сохраняется. Импорт не может передавать organization_id, секреты, ссылки на внешние файлы или бинарные модели. Экспорт содержит schema_version и конфигурацию без секретов; значения CSV, начинающиеся с `=`, `+`, `-`, `@`, защищаются от выполнения формул при открытии в табличном редакторе. JSON предназначен для точного обмена без такого изменения строк.

## 7 Сценарии и состояние диалога

### 7.1 Формат графа

Граф имеет schema_version=1, flow_id, nodes, edges и layout. Node: id UUID, type из закрытого перечня, config типизированного вида и position `{x,y}`. Edge: id, source, source_handle, target. У каждого output handle не более одной исходящей связи; условия ветвления выражаются в конфигурации соответствующего блока. Layout не влияет на выполнение, но входит в экспорт. Максимум — 300 узлов и 600 связей на агента.

В версии агента один основной граф. Повторно используемые подграфы, произвольный код и eval-выражения не поддерживаются. Ссылки на намерения, сущности и параметры используют UUID, не отображаемые подписи.

### 7.2 Типы блоков

- `start`: ровно один, без входящих связей; выход `next`. Запускается при создании диалога или входе в агента после handoff.
- `switch_intent`: выбирает выход по intent_id; выход `fallback` обязателен. Если текущая фраза уже была обработана при заполнении параметра, не использует её повторно: завершает turn в ожидании следующего сообщения, затем распознаёт новое намерение.
- `say`: формирует один текстовый ответ до 4000 символов, подставляет разрешённые slots; выход `next` обязателен. Несуществующий обязательный параметр блокирует валидацию, отсутствующее необязательное значение заменяется пустой строкой.
- `ask_slot`: запрашивает один slot, имеет prompt, entity_id или primitive parser, список проверок, лимит попыток 1–5; выходы `success`, `invalid`, `exhausted`. Если slot уже валиден, проходит success без вопроса. Иначе отправляет prompt и останавливает turn до следующей фразы. После ввода принимает значение, увеличивает счётчик неудач и выполняет нужный переход.
- `set_slot`: присваивает константу либо значение разрешённого JSON-path результата HTTP/другого slot; операции `set|clear`. Выходы `next` и `error`.
- `condition`: упорядоченный список условий и обязательная ветка `else`. Операторы `eq,ne,gt,gte,lt,lte,in,exists`; композиции `all|any` с глубиной до 3. Пустое значение отличается от 0/false; преобразование типов явно, без eval.
- `http_action`: ссылается на integration_id и декларативный запрос. Выходы `success`, `http_error`, `timeout`, `invalid_response`, `unknown_result`. Допустимые методы GET, POST, PUT, PATCH, DELETE; отображение результата в slots задаётся allowlist полей.
- `handoff`: ссылается на target_agent_id и конкретную ready target_version_id той же организации; задаёт mappings параметров, передачу истории и режим `call|transfer`. Для call выходы `returned` и `error`; для transfer — только `error`, успешная передача завершает текущую ветку без возврата.
- `return`: доступен в вызываемом агенте, возвращает только явно перечисленные значения и восстанавливает caller на выходе returned. При отсутствии caller считается завершением root-сеанса.
- `fallback`: формирует ответ для нераспознанного запроса и ожидает новое сообщение; в конфигурации указывается узел возобновления. Учитывает общий счётчик fallback.
- `end`: завершает диалог, имеет необязательный текст прощания; исходящих связей нет.

У каждого агента есть типизированные slots с code, value_type, required, default и флагом sensitive. Блок ask_slot использует entity из текущего сообщения, а при отсутствии сущности — parser согласно типу. Sensitive-значения маскируются в истории и трассировке; в состоянии диалога шифруются. Текстовые шаблоны используют только `{{slot_code}}`; HTML, функции и доступ к объектам приложения запрещены.

### 7.3 Проверка графа

До создания ready-версии сервер проверяет типы блоков, обязательные настройки, все ссылки, связность от start, обязательные выходы, корректность templates и терминальных блоков. Недостижимый узел — предупреждение; отсутствующий обязательный выход или ссылка — ошибка. Циклы разрешены только если каждый возможный проход требует нового пользовательского ввода; цикл без ожидания ввода отклоняется. Дополнительно runtime ограничивает один turn 50 переходами, пятью уровнями handoff и 20 секундами общего исполнения; при превышении выдаётся безопасный ответ и диагностический код.

Состояние диалога содержит root agent/release, стек вызовов, agent version каждого frame, текущий узел, типизированные slots, ожидание ввода, счётчики попыток/fallback, номер turn и статус. Нельзя сериализовать исполняемые Python-объекты. Idle timeout — 30 минут, абсолютный срок жизни — 24 часа. После истечения новый ввод требует создания нового сеанса; сервер возвращает `conversation_expired`.

### 7.4 Передача между агентами

При call текущий frame приостанавливается, целевой frame получает копию выбранных slots и разрешённый контекст истории. Возврат изменяет только параметры, явно описанные return_mapping; одинаковые имена не означают автоматическое объединение. При transfer текущий frame заменяется. Повторное использование текущей пользовательской фразы для NLU целевого агента задаётся флагом `forward_current_message`, по умолчанию false; уже потреблённый ввод ask_slot повторно не пересылается.

Зависимости готовых версий для handoff образуют DAG. Прямые и косвенные рекурсивные вызовы запрещены; возврат осуществляется блоком return, а не handoff назад. Изменения версий целевого агента не меняют уже созданную версию вызывающего агента. При отключённом сохранении текста передаются slots, метаданные и текущая доступная фраза; предыдущие тексты сообщений не восстанавливаются и не передаются.

### 7.5 HTTP-действия

Администратор создаёт интеграцию: имя, HTTPS base URL, разрешённые методы/пути, секрет и маску полей ответа. Редактор настраивает только относительный путь, query/body из slots и response mappings. Нельзя задавать произвольные Host/Authorization/Cookie headers или полный URL из пользовательского ввода. Секреты подставляет сервер, хранит шифрованными и никогда не возвращает после создания; ротация применяется к новым вызовам, значение секрета не входит в snapshot.

Защита запросов: HTTPS, allowlist доменов интеграции, запрет loopback/private/link-local/metadata адресов IPv4/IPv6, проверка всех DNS-ответов и соединение только с проверенным адресом. Перенаправления отключены. Ограничение пути не допускает выхода через `..`, смены host или схемы. Таймаут вызова до 8 секунд с общим бюджетом turn 20 секунд, ответ до 256 KiB, только JSON; максимум три HTTP-вызова в turn, каждый использует оставшийся бюджет. Внешнее тело не попадает целиком в логи и трассировку.

Автоповтор допустим только для GET при сетевой ошибке до получения ответа, один раз и в оставшемся бюджете. Для изменяющих запросов используется `Idempotency-Key=action_execution_id`, если интеграция поддерживает его. Перед отправкой в БД фиксируется execution ledger. После сбоя, когда неизвестно, выполнился ли POST/PUT/PATCH/DELETE, автоматическая повторная отправка запрещена; выбирается unknown_result. Точно однократное выполнение произвольного внешнего API без его поддержки идемпотентности не гарантируется.

В тестовом чате HTTP-действия по умолчанию подменяются настроенным mock-ответом. Реальный вызов требует роли администратора и отдельного включения для сеанса. Публичные пользователи не могут менять режим исполнения.

## 8 Обучение тестирование и публикация

### 8.1 Снимок и обучение

VER-01: после сохранения черновика редактор запускает подготовку версии. В транзакции создаются неизменяемый AgentVersion со снимком конфигурации и Job; outbox связывается с job_id. Повтор команды с тем же Idempotency-Key возвращает тот же результат. Снимок содержит намерения, сущности, train/test-данные, граф, slots, NLP-пороги и ссылки handoff. Хранить config_hash и отдельный nlu_hash без layout и сценарных полей.

Статусы версии: `building|ready|failed|cancelled`. Статусы задания: `queued|running|cancel_requested|succeeded|failed|cancelled`. Этапы подготовки: validation, vectorization, intent_training, entity_training, evaluation, packaging. API возвращает текущий этап и числовой progress только когда этап измерим; нельзя выдавать выдуманный общий процент.

Если nlu_hash совпадает с готовой совместимой моделью того же агента и организации, модель может быть повторно использована; граф и тесты проверяются заново. Нельзя переиспользовать модель другой организации. Снимок не меняется, пока пользователь редактирует следующий черновик. У агента не более одного незавершённого задания подготовки версии; попытка второго запуска — 409 с job_id. По умолчанию на платформе одно обучение одновременно, остальные ожидают очередь.

Задание имеет heartbeat раз в 15 секунд; отсутствие heartbeat 90 секунд после потери worker переводит его в failed с причиной worker_lost. Временный артефакт записывается в отдельный каталог и становится доступным атомарно после проверки checksum и manifest. Готовые артефакты не перезаписываются. Повторная доставка задания с terminal status ничего не обучает повторно. Отмена queued немедленная; running отменяется на безопасной границе этапа или по ограничению процесса до 60 секунд. Лимит подготовки версии — 15 минут; превышение завершает job с понятной ошибкой.

### 8.2 Отчёты

TEST-01: на отдельном test-наборе вычислять intent accuracy, macro/micro F1, precision/recall/F1 по каждому намерению, confusion matrix и список ошибок. Сущности оценивать по точному совпадению entity code и span, отдельно показывать ошибки нормализации значения. Для expected_fallback примеров считать долю правильно отклонённых запросов; для известных намерений — долю ошибочного fallback. В отчёте указывать размер каждого набора и версию модели.

Результаты ниже настраиваемых порогов дают предупреждение, а не подменяют оценку успешным статусом. Начальные пороги предупреждения — intent macro F1 0,80 и entity F1 0,80. Если тестов недостаточно, показать причину отсутствия конкретной метрики; деление на ноль и NaN недопустимы. Test-набор без train-примеров того же текста не является доказательством качества на всей предметной области.

VER-02: для публикации требуется ready-версия, отсутствие ошибок графа/данных/зависимостей, успешный smoke-run и минимум три test-примера на каждое включённое намерение. Все test-примеры должны завершить оценивание без технического сбоя. При низком F1 администратор может опубликовать только после подтверждения предупреждения с записью причины в аудит. Фиксированный порог качества не может блокировать отображение фактического результата.

### 8.3 Release и откат

VER-03: публикация создаёт неизменяемый Release с root_version_id и manifest всех достижимых handoff-версий. Все версии должны быть ready и из одной организации; manifest не содержит циклов и превышения глубины. Проверка и смена current_release_id выполняются атомарно. Секреты в manifest представлены ссылками; их действительность проверяется отдельно.

Новые разговоры используют current_release_id. Уже начатые разговоры сохраняют весь manifest старого release, включая версии вызываемых агентов. Откат переключает указатель на ранее проверенный release; повторного обучения не требуется. Деактивация канала или отзыв ключа останавливают следующие запросы немедленно, даже если разговор был создан на старом release.

Версии, на которые ссылаются release, активный разговор или другая версия, удалять нельзя. Первый выпуск не предоставляет пользователю очистку версий; фоновая очистка касается только временных/неуспешных артефактов. Квота готовых артефактов организации по умолчанию 2 GiB; превышение блокирует новое обучение с объяснением, не удаляя рабочие версии. Администратор установки может изменить квоту конфигурацией.

## 9 Исполнение и каналы

### 9.1 Единый runtime

RT-01: тестовый чат, виджет и внешний API используют один runtime-сервис. Различаются авторизация, доступность диагностики, mock-режим и выбор версии. Тестовый сеанс закрепляет выбранную ready-версию и manifest; редактируемый черновик напрямую не исполняется. Для проверки изменений пользователь сначала создаёт ready-версию.

Сообщение обрабатывается синхронным HTTP-запросом с ограничением 20 секунд на интерпретатор и 25 секунд на запрос в целом. NLP, если он блокирует event loop, выполняется в ограниченном пуле; тренировка никогда не выполняется в API. Браузер показывает состояние обработки и не отправляет следующий ввод до окончания текущего.

На один разговор допускается только один in_progress turn. В короткой транзакции runtime проверяет conversation credential, резервирует turn с sequence и fencing token, фиксирует processing_turn_id, затем выполняет вычисления вне длинной транзакции БД. Checkpoint и завершение записываются только при совпадении fencing token. Lease обработки — 30 секунд; watchdog завершает зависшую обработку не позднее 60 секунд. Второе одновременное сообщение получает 409 `conversation_busy` с Retry-After. Следующий запрос не может обогнать предыдущий.

RT-02: каждый POST сообщения содержит client_message_id и Idempotency-Key. Их уникальность ограничена conversation_id. Сервер хранит digest запроса: повтор ключа с другим текстом — 409. Повтор завершённого запроса возвращает прежний результат, если сохранение текста включено. При отключённой истории возвращается receipt с turn_id, статусом completed, `replayed=true`, `replay_available=false`, пустым messages; действие не выполняется заново. Идентификаторы завершённых turns хранятся до окончания сеанса и ещё 24 часа без текста. Клиент удерживает полученные сообщения в памяти вкладки и не добавляет receipt как ответ бота.

Выполнение внешнего действия отмечается отдельным execution ledger; после crash незавершённый turn не переигрывается автоматически. Ошибка отдаёт безопасное сообщение и trace_id; новый ввод возможен после восстановления согласованного checkpoint или явного перезапуска разговора. Разрыв соединения клиента сам по себе не отменяет действие; повтор запроса использует тот же ключ.

### 9.2 Внешний API

Администратор создаёт ключ для конкретного агента с правами `conversation:create` и `message:send`. Ключ непрозрачный, показывается один раз, в БД хранится хеш; метаданные — prefix, название, создатель, created_at, expires_at, last_used_at, revoked_at. Срок по умолчанию 90 дней, максимум 365. Отзыв немедленный. Ключ передаётся только в Authorization Bearer, не в URL.

Создание разговора возвращает отдельный conversation_token, ограниченный одним разговором; серверный клиент хранит его вместе с API key. Для чтения/отправки нужны оба. Один API key не даёт чтение истории всех разговоров и не открывает кабинет. Лимиты по умолчанию: 5 сообщений/с на ключ и 10 сообщений/с на организацию с burst 20; ответ 429 с Retry-After. Общая целевая нагрузка установки не отменяет эти лимиты.

### 9.3 Виджет

Канал widget содержит public channel_id, агент, enabled, точный allowlist origins, название, приветствие, цвет акцента и положение кнопки. Wildcard `*` запрещён на production; localhost разрешён только в development. Публичный идентификатор не считается секретом. Ни API key, ни session cookie кабинета в код вставки не включаются.

Загрузчик создаёт iframe на origin платформы и передаёт parent origin через postMessage с точным targetOrigin. Сервер отдаёт страницу iframe с CSP `frame-ancestors` из allowlist канала; bootstrap проверяет postMessage origin и issuing origin. Iframe получает короткоживущий widget session token в памяти, ограниченный каналом и разговором. Токен не передаётся родительской странице; сторонние cookie не требуются. На перезагрузку страницы допускается новый разговор; восстановление между вкладками/устройствами не входит в первый выпуск.

Проверка origin защищает браузерное встраивание, но не является аутентификацией клиента за пределами браузера. Против злоупотребления использовать ограничения по IP/каналу, длине запроса и числу созданий сеансов; не обещать недоступность публичного бота скриптам. Начальный лимит bootstrap — 20 новых разговоров/мин на IP и канал, burst 5. Отключённый канал или агент без публикации показывает понятное сообщение без внутренних деталей.

Текст ответов выводится как plain text. Ссылки распознаются только для http/https и открываются с безопасными атрибутами. Произвольные HTML/Markdown-вставки, скрипты и iframe внутри ответов запрещены. Виджет работает при ширине сайта от 320 px, поддерживает клавиатуру и не перекрывает весь экран без действия пользователя.

## 10 Данные и хранение

### 10.1 Общие правила модели

UUID используется для внешних идентификаторов, timestamptz — для времени; API отдаёт UTC ISO 8601. Интерфейс показывает локальную временную зону пользователя; timezone отчётов выбирается явно, по умолчанию UTC. Суммы/числовые slots не сериализуются двоичным float там, где нужна точность; number в API использует decimal string с валидатором. Строковые enums описываются в OpenAPI.

Изменяемые ресурсы имеют revision, created_at, updated_at и updated_by. Уникальные ограничения определяются в БД, а не только фронтендом. Составные внешние ключи и RLS проверяются миграциями и интеграционными тестами. Удаление связанных записей не допускает висячих ссылок.

### 10.2 Основные записи

- `User`: id, email_normalized unique, password_hash, email_verified_at, status. `AuthSession`: token_hash, user_id, idle/absolute expiry. `AuthToken`: purpose, token_hash, expires_at, consumed_at.
- `Organization`: id, slug unique, name, owner_user_id, history_retention_days 1–30, store_message_text, status. `Membership`: organization_id, user_id, role, unique pair. `Invitation`: email, role, token_hash, expires_at, status.
- `Agent`: organization_id, id, slug unique within organization, name, description, language, status, current_release_id. `AgentDraft`: agent_id unique, revision, schema_version, config JSONB. Config включает intents, entities, examples со split, slots, flow, nlu_settings.
- `EditLease`: organization_id, agent_id unique, holder_user_id, holder_tab_id, token_hash, fencing_counter, expires_at. Счётчик не сбрасывается при передаче аренды.
- `AgentVersion`: organization_id, agent_id, id, monotonically increasing number, status, source_revision, config_snapshot JSONB, config_hash, nlu_hash, model_artifact_id, validation_report, created_by. После ready содержимое immutable.
- `Artifact`: organization_id, id, private storage_key, kind, size, sha256, manifest_version, created_at, status. Пользователь не задаёт storage_key. `Release`: organization_id, agent_id, id, root_version_id, dependency_manifest JSONB, created_by, created_at, reason.
- `Job`: organization_id, id, kind, resource_id, status, stage, progress nullable, heartbeat_at, attempts, error_code, safe_error_message, created_by, timestamps. `OutboxEvent`: id, job_id/event_type, published_at, attempts, next_retry_at; payload не содержит исходных сообщений и секретов.
- `EvaluationReport`: organization_id, version_id, job_id, counts, metrics JSONB, confusion_matrix JSONB, per_example_results artifact reference. Отчёт связывается с неизменяемым test-набором snapshot.
- `Conversation`: organization_id, id, channel_type, channel_id/key_id, root_agent_id, release_id nullable для test, version_manifest, token_hash, state JSONB, status, next_sequence, processing_turn_id, last_activity_at, expires_at.
- `Turn`: organization_id, conversation_id, id, sequence unique, client_message_id unique within conversation, idempotency_key_hash unique within conversation, input_digest, status, fencing_token, started_at, finished_at, error_code. `Message`: organization_id, conversation_id, turn_id, role, text_encrypted nullable, timestamp. `TraceEvent`: turn_id, event_order, kind, safe_payload JSONB, duration_ms.
- `ActionExecution`: organization_id, turn_id, node_id, execution_index, request_digest, external_idempotency_key, status, safe_response_metadata, started_at, finished_at. Unique `(turn_id,node_id,execution_index)`.
- `Integration`: organization_id, id, name, allowed_origin/path/methods, encrypted_secret, secret_key_version, revision. `ApiKey`: organization_id, agent_id, token_hash, scopes, expiry/revocation, prefix. `WidgetChannel`: organization_id, agent_id, allowed_origins, settings, enabled.
- `AuditEvent`: organization_id, actor_type/id, action, resource_type/id, timestamp, request_id, safe_changes. `HourlyMetric`: organization_id, agent_id, channel_type, bucket_utc, intent_id nullable, version_id, counters, latency_histogram. `ImportPreview` и `ExportJob` — временные записи с TTL и авторизацией доступа.

Фраза и её spans являются частью draft/snapshot JSONB; отдельные таблицы примеров в первой версии не обязательны. Сервис предоставляет адресную валидацию каждого элемента. Переход к нормализованным таблицам допустим только с сохранением внешнего контракта и атомарности черновика.

### 10.3 История приватность и очистка

По умолчанию текст входящих/исходящих сообщений и безопасная диагностика хранятся 30 дней. Владелец/администратор может установить срок 1–30 дней или отключить сохранение текста. Настройка применяется к новым сообщениям сразу; сокращение срока ставит очистку уже сохранённых данных. Отключение сопровождается выбором «удалить ранее сохранённый текст», по умолчанию включённым. Удаление выполняется не позднее 24 часов; до завершения уже скрыто в обычных списках.

При store_message_text=false исходный текст обрабатывается в памяти API и не записывается в БД, broker, outbox, дисковые журналы, error tracking или telemetry. Сохраняются числовые метрики, коды намерений/ошибок и технические receipt без текстовых полей/значений сущностей. Состояние необходимых slots всё равно временно хранится для исполнения; чувствительные slots шифруются и маскируются. Это явно объясняется рядом с переключателем настройки. После окончания/истечения разговора все slots и runtime checkpoint очищаются не позднее часа. Текст пользовательских обучающих примеров регулируется жизненным циклом конфигурации, а не историей разговоров.

При включённой истории handoff получает не более 20 последних сообщений и 16000 code points; обрезка помечается в трассировке. Sensitive-значения маскируются до передачи истории. HTTP body, auth headers, секреты, токены и password никогда не сохраняются в trace. Хранить шифрование текста сообщений отдельно от маскирования UI; ключи находятся вне БД и резервируются отдельно.

Экспорт истории доступен только владельцу/администратору, содержит JSON или защищённый CSV, фильтры и отметку времени. Ссылка на скачивание доступна только авторизованному участнику с правом экспорта, привязана к организации, действует 15 минут; файл удаляется через час. Секреты и скрытые sensitive-значения в экспорт не включаются. Наблюдатель не скачивает артефакт прямой ссылкой.

Аудит административных действий хранится 180 дней без содержимого сообщений; агрегаты — 90 дней, без conversation/user identifiers. Удаление истории по запросу удаляет сообщения/trace, не меняя уже обезличенные агрегаты. Резервные копии хранятся 7 дней; после восстановления до открытия доступа повторно применяются актуальные настройки retention и журнал удалений, чтобы не вернуть удалённую историю. Это техническая политика хранения, а не заявление о соответствии конкретному законодательству.

## 11 Контракт HTTP API

### 11.1 Соглашения

Все маршруты имеют префикс `/api/v1`. Кабинет использует cookie+CSRF, runtime — отдельную авторизацию. Ответ объекта возвращается напрямую, список — `{items,next_cursor}`; page size 25 по умолчанию, максимум 100. Cursor непрозрачный; сортировка детерминирована через `(created_at,id)`. Фильтры и допустимые sort-поля явно перечисляются схемой каждого списка. Для временных фильтров from включительно, to исключительно.

Имена JSON — snake_case. Длительности указываются с суффиксом `_ms`, размер — `_bytes`. PATCH изменяет только переданные поля; null разрешён только для nullable. Скрытые поля не принимаются в mass assignment. Неизвестные поля входных схем отвергаются, кроме специально версионируемых extension-объектов, которых пока нет.

Успех: 200 для чтения/обновления, 201 для созданного ресурса, 202 для задания, 204 для удаления/выхода. Ошибки: 400 некорректный запрос, 401 не авторизован/истёк токен, 403 недостаточно прав, 404 ресурс недоступен, 409 конфликт состояния/идемпотентности, 412 устаревший revision, 413 превышен размер, 422 ошибки полей, 423 занята аренда, 429 лимит, 503 временно недоступна зависимость. Для 401 публичного разговора не раскрывать факт существования conversation_id.

Ошибка имеет `{error:{code,message,details:[{path,code,message}],request_id}}`. Message предназначен пользователю, детали не содержат stack trace и секреты. X-Request-ID присутствует в каждом ответе и связан с логами. ETag для изменяемого ресурса имеет вид `"rev-42"`; If-Match обязателен на PUT/PATCH draft, канала, интеграции и настроек организации. OpenAPI описывает все ошибки и примеры; сгенерированный клиент проходит TypeScript typecheck.

### 11.2 Аутентификация и организации

- `POST /auth/register` `{email,password}` → 202 с нейтральным сообщением; `POST /auth/verify-email` `{token}` → 204; `POST /auth/resend-verification` `{email}` → 202.
- `POST /auth/login` `{email,password}` → 200 `{user,csrf_token}` и cookie; `POST /auth/logout` и `/auth/logout-all` → 204; `GET /auth/me` → user, memberships и csrf_token. `POST /auth/forgot-password` `{email}` → 202; `POST /auth/reset-password` `{token,password}` → 204.
- `GET /organizations`, `POST /organizations` `{name,slug}` → 201 Organization; `GET /organizations/{org_id}`; `PATCH /organizations/{org_id}` `{name,history_retention_days,store_message_text,purge_existing_text}`. Активная организация выбирается на клиенте через URL.
- `GET /organizations/{org_id}/members`; `PATCH /organizations/{org_id}/members/{user_id}` `{role}`; `DELETE` того же ресурса. `POST /organizations/{org_id}/leave` → 204.
- `GET|POST /organizations/{org_id}/invitations`; создание `{email,role}` → 201; `DELETE /organizations/{org_id}/invitations/{invite_id}`; `POST /organizations/{org_id}/invitations/{invite_id}/resend` → 202; `POST /invitations/accept` `{token}` → membership.
- `POST /organizations/{org_id}/transfer-ownership` `{new_owner_user_id,password}`; `POST /organizations/{org_id}/deletion` `{password,confirmation_name}` → 202 job. Для POST этих двух действий обязательны CSRF и проверка пароля, а не сохранённый флаг в UI.

### 11.3 Агенты данные и блокировки

Далее `{O}` означает `/organizations/{org_id}`, `{A}` — `{O}/agents/{agent_id}`. Это сокращение документа, в OpenAPI должны быть полные пути.

- `GET|POST {O}/agents`; создание `{name,slug,description}` → Agent и draft_revision. `GET|PATCH {A}` для метаданных с If-Match; `POST {A}/copy` `{name,slug}`; `POST {A}/archive`, `POST {A}/restore`.
- `POST {A}/edit-lease` `{tab_id}` → `{lease_token,fencing_counter,expires_at}`. `POST {A}/edit-lease/renew` с токеном/counter; `DELETE {A}/edit-lease` освобождает собственную аренду; `POST {A}/edit-lease/revoke` — администратор. GET draft включает безопасное имя держателя и expires_at, но не lease token.
- `GET {A}/draft` → `{revision,schema_version,config,validation_summary,lease}` и ETag. `PUT {A}/draft` → новый revision; тело `{schema_version,config}`, заголовки X-Edit-Lease, X-Edit-Fence и If-Match обязательны. Изменения набора данных и графа сохраняются одной атомарной операцией.
- `POST {A}/draft/validate` `{revision}` → `{errors,warnings}` с JSON-path и node_id/example_id. Запуск доступен редактору и не изменяет черновик.
- `POST {A}/imports/preview` multipart file и mode → 202 job. `GET {A}/imports/{preview_id}` → counts, conflicts, row_errors, base_revision, expires_at; TTL preview один час. `POST {A}/imports/{preview_id}/apply` требует аренду/If-Match → новый draft revision, 409 при устаревшем preview. Apply применяет сохранённый проверенный payload, а не заново переданный файл.
- `POST {A}/exports` `{format:"json"|"csv",source:"draft"|"version",version_id?}` → 202 job. `GET {O}/exports/{export_id}/download` проверяет роль, TTL и организацию. Для конфигурации экспорт разрешён редактору; для истории только администратору/владельцу.

### 11.4 Версии задания и тесты

- `POST {A}/versions` `{source_revision}` + Idempotency-Key → 202 `{version_id,job_id}`. `GET {A}/versions`, `GET {A}/versions/{version_id}` и `/report`; отчёт включает ссылки на постраничные детали ошибок.
- `GET {O}/jobs/{job_id}` → Job. `POST {O}/jobs/{job_id}/cancel` → Job; отмена разрешена создателю с действующими правами или администратору. Клиент опрашивает активные задания раз в две секунды, после 30 секунд — раз в пять; останавливается на terminal status и скрытой вкладке.
- `POST {A}/versions/{version_id}/evaluations` → 202 job, использует test-набор версии. `POST {A}/test-conversations` `{version_id,http_mode:"mock"|"live"}` → 201 `{conversation_id,conversation_token,messages}`. Последующие сообщения идут через management-маршрут `{O}/test-conversations/{conversation_id}/messages` с cookie+CSRF и отдельной проверкой организации; diagnostics доступны только там.
- `POST {A}/releases` `{version_id,warning_acknowledgement?,reason?}` → 201 Release; администратор/владелец. `GET {A}/releases`; `POST {A}/rollback` `{release_id,reason}` → 200 `{current_release_id}`. Для публикации и rollback обязателен If-Match метаданных агента, чтобы параллельный администратор не потерял обновление.

### 11.5 Интеграции каналы история

- `GET|POST {O}/integrations`; `GET|PATCH|DELETE {O}/integrations/{integration_id}`. GET никогда не возвращает секрет, только `has_secret`. `POST .../{integration_id}/rotate-secret` `{secret}`. Удаление запрещено, если интеграция используется готовой версией/активным разговором; вместо удаления доступно disable, направляющее вызов в error-ветку.
- `GET|POST {A}/api-keys`; создание `{name,expires_at?}` → metadata и secret один раз. `POST {A}/api-keys/{key_id}/revoke` → 204.
- `GET|POST {A}/widget-channels`; `GET|PATCH {A}/widget-channels/{channel_id}`; `POST .../{channel_id}/disable`; `GET .../{channel_id}/embed-code` → HTML snippet без секретов. Администратор/владелец.
- `GET {O}/conversations` с agent_id, channel_type, status, date range, intent_id и error_code; по тексту искать только при включённой истории, с маскированием и ограничением длины query. `GET {O}/conversations/{id}`; `/messages` и `/trace` возвращают cursor-списки; тестовые и реальные разговоры разделены фильтром и меткой.
- `POST {O}/history/exports` `{filters,format}` → 202 job; `POST {O}/history/deletions` `{filters,confirmation:"delete"}` → 202 job. Обе операции требуют админских прав и записывают аудит.
- `GET {O}/analytics/summary`, `/timeseries`, `/intents`, `/errors` с общими фильтрами from,to,agent_id,channel_type,timezone; `GET {O}/audit` только владелец/администратор.

### 11.6 Публичный runtime и примеры

- `POST /runtime/agents/{agent_id}/conversations` с API key → 201 `{conversation_id,conversation_token,release_id,expires_at,messages}`. Agent должен совпасть с ограничением ключа.
- `POST /runtime/conversations/{conversation_id}/messages` с API key, X-Conversation-Token и Idempotency-Key; тело `{client_message_id,text}` → 200 runtime result. `POST .../close` → 204. `GET .../receipt/{client_message_id}` → технический статус без внутренней трассировки.
- `POST /widget/channels/{channel_id}/sessions` с проверенным браузерным bootstrap → 201 token и conversation_id. `POST /widget/conversations/{id}/messages` принимает только widget bearer и Idempotency-Key; модель ответа совпадает с runtime. Widget token не подходит к management API или другим conversation_id.

Пример успешного результата публичного сообщения:

```json
{
  "conversation_id": "uuid",
  "turn_id": "uuid",
  "sequence": 3,
  "status": "waiting_input",
  "messages": [{"id": "uuid", "type": "text", "text": "Укажите номер заказа"}],
  "replayed": false,
  "replay_available": true,
  "request_id": "uuid"
}
```

Допустимый status ответа: `waiting_input|completed|failed`. Внутренний in_progress виден только через receipt при восстановлении связи. Для ожидаемого непонимания status остаётся waiting_input и возвращается fallback-ответ, а не HTTP 500. Публичный ответ не раскрывает slots, граф, секреты, NLU scores или историю других сообщений.

Дополнительное поле diagnostics management-чата:

```json
{
  "version_id": "uuid",
  "intent": {"code": "order_status", "score": 0.83},
  "alternatives": [{"code": "refund", "score": 0.11}],
  "entities": [{"code": "order_id", "start": 10, "end": 13, "value": "123", "source": "regex"}],
  "fallback_reasons": [],
  "visited_nodes": ["node-uuid"],
  "active_agent_id": "uuid",
  "duration_ms": 130,
  "trace_id": "uuid"
}
```

Это пример структуры, а не результат измерения. Sensitive values в diagnostics маскируются. Trace содержит упорядоченные события с node_id, agent_version_id, видом перехода, безопасным результатом и duration_ms. Обязательные виды: nlu_result, node_enter, slot_updated, http_started, http_finished, handoff, returned, fallback, error, turn_finished.

## 12 Требования к фронтенду

### 12.1 Навигация и общие состояния

UI-01: маршруты кабинета начинаются с `/app/o/:orgId`. Слева находятся «Обзор», «Агенты», «Диалоги», «Аналитика», «Интеграции», «Участники», «Аудит» и «Настройки» с учётом роли. В верхней части — переключатель организации, текущий пользователь и тема. Переход в другую организацию очищает query cache предыдущей организации, leases и состояние открытого тестового чата. Нельзя показать данные прошлой организации на время загрузки новой.

Общие состояния каждого экрана: loading со скелетоном, empty с объяснением следующего действия, доступная ошибка с повтором, forbidden, not found и штатное содержимое. Формы показывают ошибки у полей и общий текст ошибки. Toast используется для результата операции, но не заменяет сохраняемое объяснение ошибки. API 401 возвращает на вход с безопасным внутренним return_to; внешние redirect URL отвергаются.

Тема выбирается «Системная/Светлая/Тёмная» и сохраняется как несекретная настройка. Все цвета используют токены; состояние не определяется одним цветом. Кабинет работает от 360 px, списки при необходимости превращаются в карточки. При ширине меньше 1024 px редактор графа показывает read-only просмотр и предложение открыть его на компьютере; остальные разделы агента остаются доступны.

### 12.2 Экраны и действия

- `/login`, `/register`, `/verify-email`, `/forgot-password`, `/reset-password`, `/invitations/accept`: все auth-состояния, время действия ссылки, повторная отправка, обработка отозванного/истёкшего токена. Email берётся из формы/проверенного токена, а не произвольного URL-параметра приглашения.
- `/app/organizations`: список членств, создание организации, пустое состояние нового пользователя. После создания — короткий onboarding: создать агента, добавить данные, собрать сценарий, проверить, опубликовать.
- `/app/o/:orgId/overview`: количество агентов, активные/ошибочные задания, диалоги за выбранный период и последние административные события. Ссылки ведут к реальным отфильтрованным данным.
- `/agents`: поиск по названию/slug, фильтры active/archived и наличия публикации, создание и копирование. Показывать последнюю ready-версию, текущую опубликованную и состояние подготовки. Архивные не скрываются без возможности найти их.
- `/agents/:agentId`: оболочка редактора с вкладками «Общее», «Намерения», «Сущности», «Примеры», «Сценарий», «Обучение и тесты», «Версии», «Каналы». В шапке — аренда, сохранение, выбор версии для теста, кнопки подготовки и публикации по роли.
- `/agents/:agentId/intents`: список/редактор намерений, число train/test-примеров, зависимости и ошибки. `/entities`: методы извлечения, типы, словарь/regex, проверка выражения на примере с timeout. `/examples`: фильтры по intent и split, поиск, редактирование текста, разметка выделением, preview импорта и экспорт.
- `/agents/:agentId/flow`: палитра блоков слева, граф в центре, настройки выбранного блока справа. Масштабирование, панорамирование, minimap, создание/удаление связей, выделение, undo/redo минимум 50 действий в пределах вкладки. Undo не отменяет чужую сохранённую версию после утраты аренды. Панель проблем позволяет перейти к конкретному блоку/полю.
- `/agents/:agentId/training`: очередь и этапы задания, отмена, отчёты по метрикам, confusion matrix, ошибочные примеры, предупреждения. Матрица и графики имеют текстовые подписи; строки отчёта доступны для клавиатуры и фильтрации.
- `/agents/:agentId/versions`: номер, создатель, source_revision, config hash, дата, статус, результаты тестов; сравнение двух версий по количеству и перечню изменений намерений/сущностей/примеров/узлов. Публикация с проверками и подтверждением предупреждений, история release, откат с вводом причины.
- Панель «Тестовый чат» в редакторе: выбор ready-версии, сообщения, сброс сеанса, текущий агент/версия, распознанное намерение, сущности, fallback и дерево переходов. Клик по событию узла подсвечивает его на графе соответствующей версии. Диагностика старой версии никогда не рисуется поверх изменённого черновика без явного переключения просмотра.
- `/agents/:agentId/channels`: widget-настройки, allowlist origins, preview, код вставки; API keys с одноразовым показом, копированием и отзывом. Встроенный preview использует тестовый origin/режим и не заставляет добавлять wildcard.
- `/conversations`: таблица с фильтрами, состоянием, агентом, каналом, временем и ошибками; страница разговора с историей и безопасной трассировкой. При отключённом тексте прямо указать причину отсутствия сообщений; не показывать пустой чат как потерянные данные. Массовый экспорт/удаление доступны только администратору.
- `/analytics`: сводка, временной график количества диалогов/сообщений, частые намерения, fallback, ошибки, p50/p95 времени ответа. Общие фильтры по периоду, агенту и каналу; явная timezone и время актуальности.
- `/integrations`, `/members`, `/audit`, `/settings`: управление интеграциями без чтения секретов, приглашения/роли/отзыв, журнал изменений, название/retention/история, передача владения и удаление организации.

### 12.3 Формы редактора и валидация

Действия, меняющие конфигурацию, сначала изменяют локальный draft и сохраняются через единый PUT. При изменении одного поля нельзя потерять незагруженные примеры: полный draft загружается и валидируется до начала редактирования. Если достигнут предел 10 MiB, сохраняемый запрос отклоняется до отправки с указанием размера и способов уменьшить набор.

Клиентская проверка ускоряет ввод, но окончательной является серверная. Path серверной ошибки сопоставляется полю/примеру/узлу. Перед удалением используемого intent/entity/slot UI показывает зависимости; кнопка удаления заблокирована до их устранения. Переименование отображаемого названия не ломает ссылки по UUID.

Копирование ключа/кода вставки подтверждается в UI. Закрытие одноразового секрета предупреждает, что повторно его прочитать нельзя. Пароль при опасной операции не кэшируется и очищается после ответа. Скрытые по роли страницы не должны выполнять запрос на изменение «на всякий случай».

### 12.4 Доступность и проверка интерфейса

Основные действия доступны с клавиатуры; фокус видим, модальные окна удерживают и возвращают его. Поля имеют label и связанные ошибки, кнопки с иконкой — доступное имя. Для графа доступны список узлов и редактирование свойств без точного drag-and-drop. Минимальный контраст обычного текста 4,5:1, интерактивных границ 3:1. Пользовательское уменьшение анимаций учитывается.

Проверить текущую и предыдущую основные версии Chrome, Firefox и Safari на дату приёмки. Проверить ширины 360, 768, 1280 и 1440 px; светлую и тёмную темы; длинные русские подписи, пустые/ошибочные данные и истёкшую сессию. Публикация интерфейса не допускает обрезанных важных кнопок, перекрытий и горизонтального скролла всей страницы за исключением рабочей области графа.

## 13 Аналитика наблюдаемость и аудит

### 13.1 Определения метрик

Количество диалогов — число созданных production-разговоров в периоде; тестовые не включаются по умолчанию. Сообщения — принятые пользовательские turns, без повторов Idempotency-Key. Популярные намерения считаются по root/активному агенту, явно указанному в фильтре, один NLU-result на фактическое распознавание; handoff не создаёт второй пользовательский turn.

Fallback rate = turns, в которых произошло хотя бы одно событие fallback, / turns с попыткой NLU. Error rate = технически failed turns / все завершённые turns; fallback не считается технической ошибкой. Latency измеряется от принятия сообщения API до завершения turn, включает NLP, интерпретатор и внешние вызовы; отдельно возвращаются internal_latency и external_http_latency. Для p50/p95 использовать фиксированные histogram buckets и приближённую оценку с указанием метода, а не среднее от дневных p95. Если знаменатель 0, API возвращает null и count=0, UI показывает отсутствие наблюдений.

Метрики обновляются идемпотентно по завершённому turn; уникальный ключ metric_event не допускает двойного учёта. Hourly buckets хранятся в UTC; timezone используется для границ пользовательского периода. Актуальность аналитики — не хуже 60 секунд. Очистка текстовой истории не удаляет обезличенные счётчики.

### 13.2 Логи и аудит

Структурированные JSON-логи содержат timestamp, level, service, request_id/job_id/turn_id, duration_ms, safe error code. Исходный текст, slots, email в payload, заголовки авторизации и query-токены исключаются фильтрами логирования. Метрики процесса и dependency errors не должны иметь labels с user_id/conversation_id и другой неограниченной кардинальностью.

Записывать аудит: приглашение/отзыв/смена роли, передача владельца, изменение retention, создание/ротация/отзыв секретов и ключей, импорт, подготовка версии, публикация, откат, отзыв lease, экспорт/удаление истории и удаление организации. Запись содержит факт и безопасные изменения без секретов/текстов. События аудита создаются в той же транзакции, что административное изменение.

`GET /health/live` проверяет живость процесса, `GET /health/ready` — доступность БД, хранилища артефактов и совместимой схемы. Состояние broker/worker отображается в диагностике очереди; недоступный RabbitMQ допускает сохранение draft, но задания остаются queued/outbox и UI показывает задержку. Готовность runtime не должна зависеть от наличия запущенного training worker.

## 14 Нефункциональные требования

### 14.1 Нагрузка и ограничения

Целевая первая установка: до 10 организаций, 100 агентов суммарно, 100 активных conversations и 10 пользовательских сообщений в секунду на всю платформу. Активный диалог не равен одновременно выполняемому запросу. Для приёмочного профиля использовать 100 обученных небольших моделей, а сообщения распределять по десяти активным агентам; описать также холодную загрузку других моделей.

Исходный стенд: Linux x86_64, 8 vCPU, 16 GiB RAM, SSD от 80 GiB. Это планируемая конфигурация проверки, а не подтверждённая достаточность. API — два процесса; одна параллельная тренировка с лимитом 2 vCPU/4 GiB. Кэш моделей ограничен суммарно 1 GiB на API-процесс, LRU eviction не удаляет артефакты. Количество workers и лимиты корректируются по результатам измерений с записью в отчёт, без скрытого снижения целевой нагрузки.

NFR-01: при 10 msg/s в течение 15 минут после двухминутного прогрева, без реальных внешних HTTP-задержек и без обучения, p95 runtime ≤ 2 секунд, p99 ≤ 5 секунд, доля технических 5xx < 1%. Данные стенда: пять намерений и 500 train-примеров на активного агента, граф до 50 блоков. Отдельно повторить с одним обучением в фоне; p95 runtime ≤ 3 секунд. Чужие 429 из специально превышенной квоты считать отдельно, а не успехом.

NFR-02: p95 обычных GET кабинета ≤ 500 мс на том же стенде, размер страницы до 100 записей. Save draft до 1 MiB — p95 ≤ 1 секунды; для 10 MiB — ≤ 5 секунд. Старт приложения не должен загружать все модели сразу. Холодный запрос к модели измеряется отдельно, целевой p95 ≤ 5 секунд.

NFR-03: граф 300 узлов/600 связей открывается до 3 секунд на согласованном современном компьютере разработчика; приёмка фиксирует браузер/CPU/RAM. Проверить drag/zoom и отсутствие длительных зависаний главного потока. Импорт и обучение никогда не блокируют UI до завершения фоновой задачи.

### 14.2 Надёжность и безопасность

NFR-04: сохранённая транзакция конфигурации не теряется после штатного перезапуска; queued job после восстановления broker запускается один раз логически. Restart worker не создаёт вторую ready-версию и не оставляет бессрочный running. Изменение схемы БД не выполняется из каждого API-worker при старте: migration — отдельный одноразовый шаг.

NFR-05: доступ между организациями запрещён на API, файлах, заданиях, runtime credential и запросах БД. Проверять не только чтение по UUID, но и списки, экспорт, nested IDs, callback/idempotency lookup и stale cache. Неучастник не может узнать существование приватной записи через различие тела ошибки.

NFR-06: TLS на production, секреты вне Git и клиентского bundle, контейнеры приложений без root, БД/broker не имеют публичных портов. На клиенте нет dangerouslySetInnerHTML для пользовательских данных. CSP, безопасные cookies, CSRF, параметры SQL, лимиты payload, защита HTTP-интеграций и приватный artifact download являются обязательными, а не задачами «после релиза».

NFR-07: резервная копия БД и volume артефактов ежедневно, хранение семь дней, шифрование копий. Цели первого выпуска: RPO ≤ 24 часов, RTO ≤ 4 часов. Приёмка включает восстановление на пустой стенд и запуск закреплённого release, проверку RLS и retention. Цели не считаются достигнутыми по одному наличию cron/backup-команды.

NFR-08: production-логирование не сохраняет текст при store_message_text=false даже при исключении, NLU-error или HTTP-timeout. Отдельный тест использует уникальную контрольную строку и ищет её в БД, broker payload, файлах и логах. Runtime slots, необходимые для продолжения диалога, проверяются отдельно и удаляются по TTL.

## 15 Развёртывание структура и эксплуатация

### 15.1 Структура рабочей области

В текущей рабочей области `frontend/` и `backend/` являются отдельными Git-репозиториями. Сохранять их `.git`, историю и лицензии. Не создавать общий родительский репозиторий и не преобразовывать их в submodules без отдельного решения владельца.

`frontend/` содержит приложение, widget entrypoint, generated API client, компонентные и e2e-тесты. `backend/` содержит app, миграции, workers, тесты, Dockerfile, compose-файлы и эксплуатационные скрипты. `backend/compose.yaml` в локальной рабочей области может ссылаться на `../frontend`; инструкция развёртывания описывает клонирование обоих репозиториев рядом. Production использует собранные образы с закреплёнными тегами.

Согласованные документы хранятся в общем `docs/` рабочей области. На S01 сохранить их копии в `backend/docs/product/` для версионирования и добавить во frontend README ссылку на backend-репозиторий/документацию после проверки существующего remote. Не выдумывать URL репозитория. Синхронизировать копии при изменении требований; исходным редактируемым местом до переноса остаётся общий docs. Содержимое документации нельзя потерять из-за того, что родительская папка не является Git-репозиторием.

### 15.2 Профили и команды

Development: PostgreSQL/RabbitMQ/Mailpit и приложения с hot reload; тестовая HTTP-интеграция — отдельный mock-service только development/test. Чтобы тестировать SSRF-защиту без разрешения всех private IP, mock-интеграция включается явным dev-only флагом, который запрещён при APP_ENV=production. Демоданные создаются отдельной идемпотентной командой, не при каждом старте.

Production: только собранные образы, HTTPS-domain, реальный SMTP, закрытые внутренние сети, persistent volumes и healthchecks. `.env.example` содержит имена/описания без рабочих секретов. Обязательные настройки: APP_ENV, PUBLIC_BASE_URL, DATABASE_URL, BROKER_URL, SMTP_HOST/PORT/USER/PASSWORD/FROM, encryption key и его version, SESSION_SECRET, artifact root, лимиты обучения и квоты. При отсутствии обязательной production-настройки приложение завершается с безопасной диагностикой.

README описывает точные команды install/build/up/migrate/seed/test/backup/restore, порядок обновления, получение предыдущего образа и проверку после отката. Для первого запуска достаточно клонировать репозитории, заполнить env, собрать, выполнить миграции и открыть кабинет; секретов по умолчанию и универсального admin/admin нет.

### 15.3 CI

Frontend CI: установка по lock-файлу, lint, typecheck, unit/component tests, production build и проверка generated API client. Backend CI на Python 3.14: `uv sync --locked`, `uv run --locked ruff format --check .`, `uv run --locked ruff check .`, `uv run --locked ty check`, `uv run --locked pytest` на реальном PostgreSQL с RLS, миграции empty→head и проверка модели/миграций, contract tests и smoke train/predict. Версии uv, Ruff и ty закреплены; эти же команды доступны локально. Интеграционный pipeline собирает оба приложения, запускает Compose test-profile и Playwright e2e.

Изменение API требует обновления OpenAPI, клиента и contract tests в обоих репозиториях. Сгенерированный клиент нельзя вручную править как способ скрыть несовместимость. Docker build и dependency audit должны завершаться без известных необработанных критических проблем; исключение требует точной причины и срока, а не общего ignore.

## 16 Приёмочные сценарии

Каждый сценарий выполняется на работающем бэкенде; заглушки допустимы только для явно обозначенного внешнего HTTP-сервиса и SMTP в тестовой среде.

- AC-01: пользователь регистрируется, получает письмо в Mailpit, подтверждает адрес, создаёт организацию, приглашает второго пользователя и переключается между двумя организациями. Восстановление пароля отзывает старую сессию.
- AC-02: для каждой роли проверены положительные и запрещённые действия через UI и прямой API. Вторая организация с похожими кодами намерений не видит конфигурации, задания, модели, history export и разговоры первой; прямой SQL под app-role с неверным/отсутствующим RLS-контекстом не раскрывает записи.
- AC-03: два браузера открывают одного агента; только первый редактирует. После отзыва/истечения аренды старый token не сохраняет данные. Потеря сети не вызывает молчаливую потерю или перезапись изменений.
- AC-04: импорт корректного CSV/JSON добавляет данные; ошибочный файл не меняет draft. Дубликат между train/test, неверный span, emoji offset и удаление используемой сущности дают адресные ошибки.
- AC-05: по данным двух демонстрационных агентов создаются ready-версии. Каждый содержит пять намерений, минимум десять train и пять test-примеров на намерение, не менее 20 отдельных unknown test-фраз. На этом демонстрационном наборе целевые intent macro F1 ≥ 0,85, exact-span entity F1 ≥ 0,85 для размеченных сущностей и доля отклонённых unknown ≥ 0,80. Набор фиксируется до окончательной настройки; подмена test-примеров train-фразами запрещена. Эти пороги относятся к демонстрационному набору, а не всем данным клиентов.
- AC-06: бот спрашивает номер заказа, проверяет формат, вызывает mock API, сохраняет только разрешённые поля и отвечает. Проверены 404/500, timeout, некорректный JSON, превышение размера и неизвестный результат изменяющего вызова. Опасный URL/private IP/redirect отклонён.
- AC-07: root-агент вызывает второго, передаёт выбранный параметр, второй уточняет данные и возвращает явный результат; остальные slots не перезаписываются. Попытка чужой организации/цикла/depth overflow отвергается. С отключённой историей предыдущий текст не передаётся.
- AC-08: во время разговора на release A публикуется B. Старый разговор и handoff остаются на manifest A; новый использует B. После отката новые разговоры идут по A. Рабочий агент отвечает во время обучения нового snapshot.
- AC-09: виджет встраивается на разрешённый origin без сторонних cookies, работает на 320 px и отвергается браузером на другом origin. В коде вставки отсутствует секрет. Отозванный API key, чужой conversation_token и токен другого канала не принимаются.
- AC-10: два одинаковых POST с одним ключом не дублируют ответ/метрику/HTTP-действие. Второе отличающееся сообщение с тем же ключом даёт 409. Параллельные разные turns не меняют порядок; restart API во время действия не приводит к автоматическому повторному POST во внешнюю систему.
- AC-11: при отключённом тексте контрольная строка отсутствует в постоянном хранилище и логах; expiry очищает slots. Изменение retention, экспорт и удаление выполняются с правильными правами, TTL и аудитом.
- AC-12: сводка считает fallback отдельно от технических ошибок, не включает test-сессии по умолчанию, не удваивает повторный turn; p95 и timezone соответствуют документированному методу.
- AC-13: выполнен нагрузочный профиль NFR-01/02 и отдельно профиль с обучением. Отчёт содержит стенд, dataset, команды, длительность, p50/p95/p99, ошибки, CPU/RAM и вывод о соответствии. Провал порога не помечается «готово».
- AC-14: чистый запуск из README проходит без ручной правки исходников; backup восстанавливается на пустой стенд. Пройдены пустые/ошибочные состояния интерфейса, обе темы, адаптивность и клавиатурные основные сценарии.

## 17 Комплект результата разработки

Результат первого выпуска — исходники двух приложений, lock-файлы, миграции, Docker-сборки и Compose, OpenAPI и generated client, автоматические проверки, демоданные и mock-интеграция, инструкции запуска/обновления/backup/restore и отчёт приёмки по AC-01–AC-14. Изображения UI и фиктивные API-ответы сами по себе не подтверждают готовность функции.

Реализующий агент ведёт `docs/IMPLEMENTATION_STATUS.md`: текущий этап, выполненные пункты, команды/результаты проверок, миграции, изменённые контракты и известные блокировки. После прерывания работа продолжается с этого файла и проверки реального состояния репозиториев. Выпуск завершён только после прохождения всех обязательных сценариев и устранения блокирующих дефектов; отсутствие production SMTP/domain фиксируется отдельно и не мешает подготовить и проверить полную локальную установку.
