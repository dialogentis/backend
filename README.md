# Dialogentis backend

FastAPI, Python 3.14.6, SQLAlchemy/Alembic, PostgreSQL 18, Taskiq/RabbitMQ. Зависимости устанавливаются через uv по `uv.lock`; Ruff и ty используются для проверок. Отдельные Git-репозитории backend и frontend должны находиться рядом.

Кабинет поддерживает рабочие пространства, управление участниками, редактирование агентов, обучение, тестовый чат, публикацию и откат. Внешний API запускает диалоги на опубликованных версиях.

## Первый запуск

Требуются Docker с Compose 2.24.4+ и uv 0.11.29. Все команды выполняются в backend.

```sh
uv sync --locked
uv run --locked python scripts/init_env.py
docker compose --profile dev up --build -d
```

Генератор создаёт `.env` с непредсказуемыми паролями и ключами (права 0600), не выводит значения и отказывается перезаписывать существующий файл. `.env.example` описывает параметры. Не заменяйте существующий `.env` без согласованной смены паролей в БД/broker: init SQL выполняется только на новом volume.

- Кабинет и API через Caddy: http://localhost:18080
- OpenAPI UI: http://localhost:18080/api/docs
- Liveness: http://localhost:18080/api/health/live
- Readiness проверяет БД, схему и артефакты на http://localhost:18080/api/health/ready. Состояние RabbitMQ и рабочих процессов показывает очередь на странице «Обзор».
- API напрямую для разработки: http://localhost:18000
- Почтовый интерфейс Mailpit: http://localhost:18025

Миграции выполняются отдельным одноразовым сервисом до запуска API. Приложение работает под `dialogentis_app`, миграции — под `dialogentis_migrator`. Bootstrap superuser недоступен приложению. Одноразовый `dispatcher-init` создаёт ограниченную роль диспетчера и её случайный пароль в отдельном Docker volume, недоступном API. Для миграций вне Compose роль диспетчера необходимо предварительно создать от имени администратора БД. PostgreSQL и RabbitMQ не публикуют порты на хост. Порты локальной разработки привязаны к loopback.

## Production

На Linux-сервере подготовьте публичное имя, DNS-записи и доступ к портам TCP 80 и 443. Для новой установки создайте отдельный файл параметров.

```sh
uv run --locked python scripts/init_env.py --output .env.production
```

В `.env.production` задайте `PUBLIC_HOST` без схемы и порта, `SMTP_HOST`, `SMTP_PORT=587` и `SMTP_FROM`. Для SMTP с аутентификацией задайте одновременно `SMTP_USER` и `SMTP_PASSWORD`. Ретранслятор должен поддерживать STARTTLS. Compose формирует публичный адрес `https://PUBLIC_HOST` из имени. Задайте `DELETION_JOURNAL_VOLUME` с именем заранее созданного независимого тома журнала. Требования к тому, копиям и процедурам восстановления и обновления описаны в [инструкции эксплуатации](docs/OPERATIONS.md).

```sh
docker compose --env-file .env.production -f compose.yaml -f compose.production.yaml up --build -d --wait
```

Caddy получает сертификат и перенаправляет HTTP на HTTPS. Только Caddy публикует порты. Он и процессы приложения работают без root. Данные PostgreSQL, RabbitMQ, артефактов, журнала удалений и Caddy находятся в отдельных томах. Ограничения ресурсов заданы в `compose.production.yaml`; значения проверяются под нагрузкой на этапе S15.

## Разработка с hot reload

```sh
docker compose -f compose.yaml -f compose.dev.yaml --profile dev up --build -d
```

Vite доступен на http://localhost:5180 (чтобы не занимать уже используемый 5178); API — на 18000. Исходники подключены read-only, зависимости находятся в образах. `/api` Vite проксирует к API. Для обычного запуска интерфейса вне Docker используется `npm run dev` в соседнем frontend, proxy по умолчанию смотрит на 18000.

## Проверки и миграции

```sh
make check
make test
make integration
docker compose run --rm migrate
uv run --locked python scripts/export_openapi.py
```

`make integration` создаёт отдельный Compose-проект `dialogentis-test` с пустыми PostgreSQL/RabbitMQ/Mailpit, выполняет тесты и удаляет только его контейнеры и volumes. Development-данные не затрагиваются. Проверяются train/predict intent/CRF, безопасное отклонение неподдерживаемых RE2 выражений, API, ручной ack Taskiq с publisher confirms, повторный запуск миграций и отсутствие drift, RLS/составные FK/возврат соединения в pool. Без `RUN_INTEGRATION=1` интеграционные тесты явно пропускаются, а не подменяются SQLite. Локальный `.env` содержит Docker DNS-имена, поэтому интеграционные проверки выполняются в Compose.

Добавлены tenant-таблицы Job/outbox, диспетчер с ограниченной ролью, worker и периодическая сверка. Compose запускает их отдельными сервисами. Доставка, повтор сообщения после ошибки фиксации БД, дедупликация запуска, восстановление и отправка некорректных сообщений в dead-letter проверены на PostgreSQL и RabbitMQ. Первый прикладной обработчик удаляет организацию; требования к независимому хранению журнала удалений и восстановлению описаны в [ORGANIZATION_DELETION.md](docs/ORGANIZATION_DELETION.md). Рабочие очереди обучения относятся к S07.

CI-команды описаны в Makefile и `.github/workflows/backend.yml`. `openapi.json` генерируется из приложения. Документы продукта версионируются в `docs/product`; актуальный журнал и решения — в `docs`.

[Два демонстрационных агента](benchmarks/nlu/README.md#демонстрационные-агенты-выпуска) импортируются в кабинет как JSON. Инструкция описывает генерацию файлов, обучение и проверку ответа.

## Авторизация и почта

Контракты доступны в `/api/docs`, все бизнес-маршруты имеют префикс `/api/v1`. Для POST/PATCH/DELETE в кабинете нужен корректный `Origin`, для запросов с сеансом — также `X-CSRF-Token`, полученный при login/me. Cookie хранит непрозрачный токен, БД хранит его SHA-256. Пароли хешируются Argon2id. В development разрешены известные локальные origins кабинета; production принимает только `PUBLIC_BASE_URL`.

Подтверждение почты (24 часа), восстановление (30 минут) и приглашения (7 дней) одноразовые. В БД хранятся хеши токенов. Письмо с исходной ссылкой до отправки хранится зашифрованным в email outbox; процесс `mailer` отправляет его через SMTP и удаляет payload. Запускается вместе с Compose или отдельно: `docker compose --profile dev up -d mailer mailpit`. При production SMTP применяется STARTTLS. Внешняя почта в локальных тестах не используется.

Доставка SMTP допускает повтор письма, если процесс завершится после отправки до фиксации БД; одноразовая ссылка остаётся безопасной. Перед сменой ENCRYPTION_KEY следует опустошить email outbox: чтение старых ключей пока не реализовано. Этим же ключом с отдельным назначением подписываются внутренние NLP-модели; его потеря или замена делает существующие модели недоступными. Механизма переноса подписей на новый ключ пока нет: сохраняйте резервную копию ключа отдельно от данных и не меняйте его до появления процедуры ротации.

`ARTIFACT_QUOTA_BYTES` ограничивает общий объём моделей организации, а `MAX_MODEL_ARTIFACT_BYTES` — размер одного модельного артефакта при записи и чтении. Уменьшение общей квоты не отключает готовые модели; отдельный предельный размер не должен быть меньше размера используемых артефактов.

Для обучения используется отдельная очередь и контейнер `training-worker`. В разделе «Обучение» можно подготовить и проверить сохранённую версию. Владелец и администратор здесь же запускают проверку готовности к публикации и управляют публикациями.

Uvicorn доверяет forwarded headers внутри стенда; Caddy перезаписывает входящие X-Forwarded-For. Порт API привязан к loopback. При внешнем production-развёртывании не публикуйте API в обход доверенного proxy.

## Внешний API

Опубликуйте готовую версию и выпустите ключ на вкладке «Каналы». Пример для клиента на сервере.

```sh
BASE_URL='http://localhost:18080/api/v1/runtime'
AGENT_ID='<agent UUID>'
API_KEY='<agent API key>'
START_KEY='<unique start request identifier>'

curl -fsS -X POST "$BASE_URL/agents/$AGENT_ID/conversations" \
  -H "Authorization: Bearer $API_KEY" \
  -H "Idempotency-Key: $START_KEY"
```

Сохраните `conversation_id` и `conversation_token` из ответа. Новые диалоги стартуют на текущей публикации. Начатый диалог продолжает работать на закреплённой публикации, включая версии вызываемых агентов.

```sh
CONVERSATION_ID='<conversation UUID>'
CONVERSATION_TOKEN='<conversation token from start response>'
MESSAGE_ID='<client message UUID>'
MESSAGE_KEY='<unique message request identifier>'

curl -fsS -X POST "$BASE_URL/conversations/$CONVERSATION_ID/messages" \
  -H "Authorization: Bearer $API_KEY" \
  -H "X-Conversation-Token: $CONVERSATION_TOKEN" \
  -H "Idempotency-Key: $MESSAGE_KEY" \
  -H 'Content-Type: application/json' \
  --data "{\"client_message_id\":\"$MESSAGE_ID\",\"text\":\"Где мой заказ?\"}"
```

При потере ответа повторите запрос с тем же ключом идемпотентности, идентификатором и текстом. Повтор использует сохранённый результат с маской `[скрыто]` для чувствительных значений. Если в организации отключено сохранение текста, повтор завершённого хода возвращает квитанцию с пустым `messages`. Технический статус доступен по `GET /conversations/{conversation_id}/receipt/{client_message_id}`; завершить диалог можно через `POST /conversations/{conversation_id}/close`. Оба маршрута принимают тот же ключ и токен диалога. При 429 учитывайте `Retry-After`. Храните ключ на сервере клиента и передавайте его только по HTTPS за пределами локального окружения.

## Виджет на сайте

В разделе «Каналы» создайте виджет и укажите точный адрес сайта, включая схему и нестандартный порт. Опубликуйте агента, откройте «Код вставки» и добавьте скрипт на страницу разрешённого сайта.

```html
<script async src="https://platform.example/widget-loader.js"
        data-dialogentis-widget="<public channel UUID>"></script>
```

Публичный идентификатор указывает на настройки виджета. После открытия чата браузер получает токен отдельного диалога и держит его в памяти iframe. Загрузка страницы заново начинает новый диалог. Для локальной проверки в development можно указать loopback origin с портом, например `http://127.0.0.1:8081`.

При строгом CSP сайта разрешите домен платформы для `script-src` и `frame-src`. Платформа ограничивает встраивание своим списком разрешённых сайтов. Если отключить канал или убрать адрес сайта из списка, следующие запросы диалога прекратятся.

## Выгрузка истории

Владелец и администратор могут заказать JSON или CSV через «Диалоги → Экспорт истории». В выгрузку попадают записи по выбранным фильтрам агента, канала, состояния и дат. Файл содержит время подготовки, фильтры, события сценария и разрешённый к хранению текст с масками.

Выгрузка готовится в очереди. Скачивание доступно до 15 минут и прекращается при истечении срока записей или изменении настроек пространства. Сервер проверяет текущие права при каждом скачивании. Временный зашифрованный файл удаляется при периодической очистке спустя час. Предел одного файла — 10 МиБ и 10 000 записей.

## Остановка сервисов

```sh
docker compose --profile dev --profile test down
```

Volumes сохраняются. При обычном обновлении сохраняйте тома базы и данных. Перед сменой версии выполните [резервное копирование](docs/OPERATIONS.md#ежедневная-копия).
